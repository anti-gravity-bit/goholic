Chapter 5: HTTP Without the Magic

By Abir Sarkar · 12 min read · Published 2026-10-03 · LinkedIn

The handler we wrote in Chapter 4 works, and it makes a dozen decisions we never examined. Why does it return 201 instead of 200? Why does it set a Content-Type header? What does a client see when the body is too large? Why did the router answer a PUT with a plain-text error?

Most developers use HTTP for years without being able to answer these questions, because frameworks hide the protocol behind conveniences. This chapter removes the conveniences. We look at the actual bytes, learn what each part of a message means, and then use that understanding to harden POST /tasks.

TCP Delivers Bytes, HTTP Gives Them Meaning

Start with the layer underneath. TCP provides an ordered, reliable stream of bytes between two endpoints. It does not know what the bytes mean, and it does not know where one message ends and the next begins. HTTP is the agreement that supplies meaning and boundaries on top of that stream.

Layer What it provides What it does not provide
TCP Ordered, reliable delivery of a byte stream Message boundaries, meaning, request and response pairing
HTTP Message framing, methods, status codes, headers, semantics Knowledge of whether the server acted on a request that was cut off

The last cell in that table is the most important sentence in the chapter. Suppose a client sends POST /tasks and the connection dies before a response arrives. The client now knows nothing. The server may never have received the request, may have received it and failed, or may have created the task and been unable to say so. Every retry decision a client makes is a guess, and later in this chapter we will see why that makes idempotency a first-class design concern.

HTTP/2 and HTTP/3 change how messages are packaged on the wire, but the semantics, meaning methods, status codes, and headers, are the same. Go’s server speaks HTTP/2 automatically over TLS, so everything here applies unchanged.

What a Message Looks Like

HTTP/1.1 is plain text. You can type a request by hand. With the Forge server running, try:

printf 'GET /tasks HTTP/1.1\r\nHost: localhost:8080\r\nConnection: close\r\n\r\n' | nc localhost 8080

A request has three parts: a start line, headers, and an optional body, separated by blank lines.

POST /tasks HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Content-Length: 29

{"title":"Write chapter one"}

The start line holds the method, the path, and the version. Each header is a name and a value. The blank line marks the end of the headers, and everything after it is the body. The response mirrors that structure, with a status line in place of the request line:

HTTP/1.1 201 Created
Content-Type: application/json
Location: /tasks/tsk_8f3a1c9d2b47
Date: Sat, 03 Oct 2026 09:14:00 GMT

{"id":"tsk_8f3a1c9d2b47","title":"Write chapter one","status":"pending", ... }

The response above is abridged, but nothing in it is magic. A browser, curl, and a Go client all produce and consume exactly this text. The Content-Length: 29 header is how the receiver knows the body ends after 29 bytes, which is TCP’s missing message boundary supplied by HTTP.

Methods Are Promises

The method is not decoration. It makes a promise about the request, and clients, caches, proxies, and retry logic all rely on that promise.

Method Safe Idempotent Used in Forge for
GET Yes Yes Reading one task or the list
POST No No Creating a task, and later, changing its state
PUT No Yes Replacing a resource (not yet used)
PATCH No Not guaranteed Partial updates (not yet used)
DELETE No Yes Removing a resource (not yet used)

Safe means the request does not change server state. A crawler or a prefetching browser may issue a GET freely, so a GET that deletes data is a serious bug. Idempotent means that sending the same request many times has the same effect as sending it once. That property is what lets a client retry after a timeout without worrying about the consequences.

POST is neither, and that is why POST /tasks has the retry problem we flagged as an open question in Chapter 3. Note that the protocol only declares the promise. Nothing enforces it. If you write a GET handler that modifies data, HTTP will not stop you, and the first proxy that retries it will punish you.

Status Codes Tell the Client What to Do

A status code answers two questions for the client: whose fault was it, and should I try again? The families encode this.

Family Meaning Client’s usual response
2xx It worked Proceed
4xx The request is wrong Fix the request. Retrying it unchanged will fail again
5xx The server failed Possibly retry later, if the operation is safe to repeat

These are the codes Forge uses, and the cases that produce them.

Code Name Forge returns it when
200 OK A read or update succeeds
201 Created POST /tasks creates a task, with a Location header
400 Bad Request The body is malformed, or a field fails validation
404 Not Found The task or route does not exist
405 Method Not Allowed The path exists but not for this method
409 Conflict The request is valid but clashes with current state (Chapter 6)
413 Content Too Large The body exceeds the size limit
415 Unsupported Media Type The Content-Type is not JSON
500 Internal Server Error An unexpected failure on our side
503 Service Unavailable A dependency is down; the client may retry later

Choosing between 400 and 422 for validation failures is a long-running argument. Some APIs use 422 for “well-formed but semantically invalid.” Forge uses 400 for all input problems, because a single rule is easier for clients to implement than a distinction few people remember. The lesson is that consistency matters more than which side you pick.

Headers Carry the Context

Headers are metadata about the message. A handful matter for almost every service.

Header Direction Purpose
Content-Type Both The format of the body. Forge accepts and returns application/json
Content-Length Both How many bytes the body contains
Accept Request The formats the client is willing to receive
Location Response Where a newly created resource lives
Allow Response Which methods a path supports, sent with a 405
Retry-After Response How long to wait before retrying, sent with 429 or 503

JSON Is Where the Details Hide

JSON feels simple, and the decoding step is full of decisions that are easy to make by accident.

An empty body produces an end-of-file error from the decoder, which is different from malformed JSON, and a good API says “a body is required.” Unknown fields are ignored by default. A client that sends {"titel":"Write chapter one"} will get a validation error about a missing title, which is at least visible. A client that mistypes an optional field gets silent misbehavior with no error at all. Trailing data, as in {"title":"a"}{"title":"b"}, is accepted by a plain decoder, which reads one value and stops. And an oversized body can exhaust memory if nothing bounds it.

Each of these is a contract decision. For Forge we choose to be strict: reject unknown fields, reject trailing data, and cap the body at 1 MiB. Strictness has a cost, which is that clients written against a newer version of the API cannot send fields an older server does not know. For a small, controlled API that cost is worth the early error. Chapter 10 returns to this when we discuss evolution.

Content Negotiation

Content-Type says what the body is. Accept says what the client wants back. Together they let one URL serve several formats. Forge serves JSON only, so we make two decisions.

Header Forge’s decision Reason
Content-Type on requests with a body Required, must be application/json, otherwise 415 A clear error is better than guessing a format
Accept Ignored; responses are always JSON Only one format exists, so negotiating is pointless

The Content-Type value may carry parameters, as in application/json; charset=utf-8, so we parse it rather than compare strings.

Idempotency: Retries Are Inevitable

Return to the uncertainty at the start of the chapter. A client that does not receive a response must decide whether to retry, and it cannot know whether the first attempt succeeded. Most well-built clients retry on timeouts, and so do load balancers and service meshes, often silently.

Request Safe to retry blindly? Why
GET /tasks/{id} Yes Reading changes nothing
DELETE /tasks/{id} Yes The task is gone after the first call and the second changes nothing
POST /tasks No Each success creates another task

For POST /tasks, Forge today creates a duplicate on every retry. We will not fix that here, because the fix is a design in its own right: a client-supplied idempotency key that lets the server recognize a repeat. Chapter 10 builds it. What matters now is that you see the problem as a consequence of how HTTP works, and not as a bug in our handler.

The Request Lifecycle

Knowing the order of events inside the server explains several behaviors that otherwise seem arbitrary.

Phase What happens Why it matters
Accept The server accepts a TCP connection and gives it a goroutine Each connection is handled concurrently
Read headers The request line and headers are parsed ReadHeaderTimeout bounds this step
Route The mux selects a handler No match means 404 or 405
Handler runs The body is read lazily, as the handler asks for it The body is a stream, not a string
Write status and headers The first WriteHeader or Write sends them After this moment, status and headers are final
Write body The body is streamed to the client WriteTimeout bounds this step
Finish The handler returns; the connection is reused or closed Keep-alive saves the cost of a new connection

Three practical rules follow. First, set headers before writing the status. A Location header added after WriteHeader is silently dropped. Second, you cannot change your mind after the status is sent. If encoding the body fails halfway through, the client has already received a 200, and all you can do is log it, which is why writeJSON logs on failure. Third, a client that disconnects mid-request cancels the request’s context, a signal our code can observe. Chapter 24 shows how to use it.

Hardening POST /tasks

Now we apply all of this. First, a shared helper that decodes a JSON body strictly and writes an appropriate error if it cannot. It lives in handlers.go beside writeJSON.

const maxBodyBytes = 1 << 20

func decodeJSON(w http.ResponseWriter, r *http.Request, dst any) bool {
    mediaType, _, err := mime.ParseMediaType(r.Header.Get("Content-Type"))
    if err != nil || mediaType != "application/json" {
        writeError(w, http.StatusUnsupportedMediaType, "UNSUPPORTED_MEDIA_TYPE", "Content-Type must be application/json")
        return false
    }

    r.Body = http.MaxBytesReader(w, r.Body, maxBodyBytes)
    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields()

    if err := dec.Decode(dst); err != nil {
        var maxBytesErr *http.MaxBytesError

        switch {
        case errors.As(err, &maxBytesErr):
            writeError(w, http.StatusRequestEntityTooLarge, "PAYLOAD_TOO_LARGE", fmt.Sprintf("request body must be at most %d bytes", maxBodyBytes))
        case errors.Is(err, io.EOF):
            writeError(w, http.StatusBadRequest, "INVALID_ARGUMENT", "request body is required")
        default:
            writeError(w, http.StatusBadRequest, "INVALID_ARGUMENT", "request body must be valid JSON with known fields")
        }
        return false
    }

    if err := dec.Decode(&struct{}{}); !errors.Is(err, io.EOF) {
        writeError(w, http.StatusBadRequest, "INVALID_ARGUMENT", "request body must contain a single JSON value")
        return false
    }

    return true
}

The imports for handlers.go grow to include fmt, io, and mime. Notice how each branch maps a distinct failure from the JSON section to its own status code and message. The function returns a boolean: true means the destination is populated, and false means a response has already been written and the caller must stop.

With that helper, createTask becomes shorter and stricter:

func (s *Server) createTask(w http.ResponseWriter, r *http.Request) {
    var req createTaskRequest
    if !decodeJSON(w, r, &req) {
        return
    }

    title := strings.TrimSpace(req.Title)
    if err := validateTitle(title); err != nil {
        writeError(w, http.StatusBadRequest, "INVALID_ARGUMENT", err.Error())
        return
    }

    task, err := s.store.Create(title)
    if err != nil {
        log.Printf("create task: %v", err)
        writeError(w, http.StatusInternalServerError, "INTERNAL", "internal error")
        return
    }

    w.Header().Set("Location", "/tasks/"+task.ID)
    writeJSON(w, http.StatusCreated, task)
}

The Location header is set on the line before writeJSON, because writeJSON sends the status, and headers added afterward would be lost. That single ordering is the lifecycle table in action.

Tightening the contract has an immediate consequence. The curl commands from Chapter 4 sent no Content-Type header, so they now receive a 415. Every client needs updating:

curl -s -X POST localhost:8080/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Write chapter one"}'

This is a small, safe preview of a large problem. Making a contract stricter breaks callers who relied on the looser behavior, which is why a published API is expensive to change, and why Chapter 3 insisted on deciding contracts early.

Testing the Contract

Our Chapter 4 tests also break, since they send no Content-Type. That is the tests doing their job. We replace them with a helper that can send any request, and a table that covers each decision made in this chapter.

func send(h http.Handler, method, path, contentType, body string) *httptest.ResponseRecorder {
    req := httptest.NewRequest(method, path, strings.NewReader(body))
    if contentType != "" {
        req.Header.Set("Content-Type", contentType)
    }
    rec := httptest.NewRecorder()
    h.ServeHTTP(rec, req)
    return rec
}

func TestCreateTask(t *testing.T) {
    h := newTestHandler()
    const jsonType = "application/json"

    tests := []struct {
        name        string
        contentType string
        body        string
        wantStatus  int
    }{
        {"valid", jsonType, `{"title":"Write chapter one"}`, http.StatusCreated},
        {"valid with charset", "application/json; charset=utf-8", `{"title":"Write chapter one"}`, http.StatusCreated},
        {"missing content type", "", `{"title":"x"}`, http.StatusUnsupportedMediaType},
        {"wrong content type", "text/plain", `{"title":"x"}`, http.StatusUnsupportedMediaType},
        {"empty body", jsonType, ``, http.StatusBadRequest},
        {"not json", jsonType, `not json`, http.StatusBadRequest},
        {"unknown field", jsonType, `{"title":"x","colour":"red"}`, http.StatusBadRequest},
        {"trailing data", jsonType, `{"title":"x"}{"title":"y"}`, http.StatusBadRequest},
        {"missing title", jsonType, `{}`, http.StatusBadRequest},
        {"blank title", jsonType, `{"title":"   "}`, http.StatusBadRequest},
        {"title too long", jsonType, `{"title":"` + strings.Repeat("a", 201) + `"}`, http.StatusBadRequest},
        {"body too large", jsonType, `{"title":"` + strings.Repeat("a", maxBodyBytes) + `"}`, http.StatusRequestEntityTooLarge},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            rec := send(h, http.MethodPost, "/tasks", tt.contentType, tt.body)
            if rec.Code != tt.wantStatus {
                t.Fatalf("status = %d, want %d", rec.Code, tt.wantStatus)
            }
        })
    }
}

func TestCreateTaskSetsLocation(t *testing.T) {
    h := newTestHandler()

    rec := send(h, http.MethodPost, "/tasks", "application/json", `{"title":"Write chapter one"}`)

    var created Task
    if err := json.NewDecoder(rec.Body).Decode(&created); err != nil {
        t.Fatalf("decode created task: %v", err)
    }
    if got, want := rec.Header().Get("Location"), "/tasks/"+created.ID; got != want {
        t.Fatalf("Location = %q, want %q", got, want)
    }
}

func TestMethodNotAllowed(t *testing.T) {
    h := newTestHandler()

    rec := send(h, http.MethodPut, "/tasks", "", "")
    if rec.Code != http.StatusMethodNotAllowed {
        t.Fatalf("status = %d, want %d", rec.Code, http.StatusMethodNotAllowed)
    }
    if rec.Header().Get("Allow") == "" {
        t.Fatal("expected an Allow header on a 405 response")
    }
}

Update TestGetTask from Chapter 4 to use send as well. Each row in the table is one sentence of the contract, which makes the test file a readable specification of how the endpoint behaves.

Engineering Lens

What problem did we solve? We replaced inherited defaults with explicit decisions about content types, size limits, strictness, status codes, and headers, and we wrote each decision into a test.

What complexity did we introduce? A shared decoding helper and a stricter contract that breaks lenient clients. The strictness is a deliberate trade, not an accident.

What failure modes appeared? Misleading status codes, silently ignored fields, unbounded request bodies, and clients that cannot tell whether a failed request took effect.

What would break at 10× scale? Retries. At higher traffic and with more infrastructure in the path, timeouts and automatic retries become routine, and every non-idempotent endpoint produces duplicates at the same rate.

When should we not be this strict? For an internal prototype consumed by one team you can message directly, lenient decoding is fine. Strictness pays off when callers are numerous, independent, or hard to reach.

Exercises

  1. Run the nc command from this chapter against your server, then craft a POST by hand with printf and nc. What happens if you declare a Content-Length larger than the body you send?
  2. Change decodeJSON to allow unknown fields. Which tests fail? Write down one situation where leniency is the better choice for a real API.
  3. Make a GET /tasks request with Accept: text/html. What does Forge return, and is that the correct behavior under the HTTP specification? Decide whether Forge should answer 406 instead, and what that would cost clients.
  4. Move the Location header assignment to after writeJSON and run the tests. Which test catches it, and what does that tell you about the value of testing headers?
  5. Choose a public API you use. For each of its write endpoints, decide whether it is safe to retry blindly. How does the API tell you?

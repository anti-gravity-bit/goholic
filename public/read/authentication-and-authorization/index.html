Chapter 9: Authentication and Authorization

By Abir Sarkar · 22 min read · Published 2026-10-03 · LinkedIn

Run Forge and list its tasks:

$ curl -s localhost:8080/tasks

You get every task in the system, and you did not have to say who you are. You can also transition any of them. Chapter 1 described a backend as a series of decisions about state, and every decision needs inputs. We have been making decisions without one of the most important inputs there is: who is asking?

This chapter adds that input. We add users, passwords, and sessions, give every task an owner, and use the middleware and error contract from the previous chapters so that security becomes a layer instead of a rewrite. The goal is engineering judgment, not cryptography. We will decide what to build, what to buy, and what to leave out.

Two Different Questions

Two words are routinely confused, and the confusion causes real bugs.

Question Name Failure response
Who are you? Authentication 401. The caller has not proven an identity
Are you allowed to do this? Authorization 403 or 404. The identity is known but lacks permission

HTTP’s own naming is part of the confusion: the status 401 is titled “Unauthorized,” but it means unauthenticated. We use our own codes, UNAUTHENTICATED and FORBIDDEN, so that nobody has to remember the quirk.

The two questions are asked in order and by different parts of the system. Authentication is a property of the request and belongs in middleware. Authorization is a property of the request and the specific resource, so it can only be answered once the resource is known, which means it lives close to the handler.

User → Credentials → Authentication → Identity → Authorization → Resource

The Decisions

Before writing code, record the decisions, as we did in Chapter 3.

Decision Choice Reason
Password storage Salted bcrypt hash, never the password A stolen database should not reveal passwords
Credential after login Opaque random session token Revocable, simple, and has no signature footguns
Token storage on the server Only a SHA-256 hash of the token A leaked session table should not yield usable tokens
Roles member and admin Enough to demonstrate the model. More come only when needed
Task ownership Each task has one owner, fixed at creation Immutable ownership makes authorization checks race-free
Access to others’ tasks 404 for members, full access for admins Do not confirm that a resource exists to someone who cannot see it
Creating admins Never through the API. Seeded at startup An endpoint that can grant admin is a privilege escalation path

Passwords: Store Hashes, Slowly

Never store passwords, and never store them with a fast hash. Fast hashes such as SHA-256 let an attacker with a stolen table test billions of guesses per second. A password hash must be deliberately slow and salted, which is a unique random value per password so that identical passwords produce different hashes. Bcrypt does both, and it is a sound default.

This is our first dependency outside the standard library, and it deserves a deliberate decision rather than an accident. Writing your own password hashing is exactly the kind of work you should not do. Install it with:

go get golang.org/x/crypto/bcrypt

package main

import (
    "sync"

    "golang.org/x/crypto/bcrypt"
)

const (
    minPasswordBytes = 8
    maxPasswordBytes = 72
)

var bcryptCost = 12

func hashPassword(password string) ([]byte, error) {
    return bcrypt.GenerateFromPassword([]byte(password), bcryptCost)
}

func mustHash(password string) []byte {
    hash, err := hashPassword(password)
    if err != nil {
        panic(err)
    }
    return hash
}

var dummyHash = sync.OnceValue(func() []byte { return mustHash("timing-equalizer") })

Three details matter. The cost is the work factor: each increment doubles the time, and 12 takes roughly a quarter of a second on typical hardware. That is imperceptible to a person logging in and expensive to an attacker guessing at scale. It is a variable, not a constant, so tests can lower it. Bcrypt also reads only the first 72 bytes of a password, so we enforce that maximum explicitly rather than silently ignoring the rest. And mustHash panics on failure, which is the one place a panic is appropriate: it runs once, lazily, and can only fail on programmer error, so failing loudly beats limping along.

The dummyHash has a purpose we will see in a moment.

Users and Sessions

Users live in a store shaped like the task store, with one important property. The check for a taken email and the insertion happen under the same lock, which is the lesson of Chapter 6 applied again: two simultaneous registrations with the same email must produce exactly one winner.

package main

import (
    "errors"
    "sort"
    "sync"
    "time"
)

type Role string

const (
    RoleMember Role = "member"
    RoleAdmin  Role = "admin"
)

type User struct {
    ID           string    `json:"id"`
    Email        string    `json:"email"`
    Role         Role      `json:"role"`
    CreatedAt    time.Time `json:"created_at"`
    PasswordHash []byte    `json:"-"`
}

var (
    ErrEmailTaken   = errors.New("email already registered")
    ErrUserNotFound = errors.New("user not found")
)

type UserStore struct {
    mu      sync.RWMutex
    byID    map[string]User
    byEmail map[string]string
}

func NewUserStore() *UserStore {
    return &UserStore{byID: make(map[string]User), byEmail: make(map[string]string)}
}

func (s *UserStore) Create(email string, passwordHash []byte, role Role) (User, error) {
    id, err := newID("usr_")
    if err != nil {
        return User{}, err
    }

    s.mu.Lock()
    defer s.mu.Unlock()

    if _, taken := s.byEmail[email]; taken {
        return User{}, ErrEmailTaken
    }
    user := User{ID: id, Email: email, Role: role, CreatedAt: time.Now().UTC(), PasswordHash: passwordHash}
    s.byID[id] = user
    s.byEmail[email] = id
    return user, nil
}

func (s *UserStore) GetByEmail(email string) (User, error) {
    s.mu.RLock()
    defer s.mu.RUnlock()

    id, ok := s.byEmail[email]
    if !ok {
        return User{}, ErrUserNotFound
    }
    return s.byID[id], nil
}

func (s *UserStore) GetByID(id string) (User, error) {
    s.mu.RLock()
    defer s.mu.RUnlock()

    user, ok := s.byID[id]
    if !ok {
        return User{}, ErrUserNotFound
    }
    return user, nil
}

func (s *UserStore) List() []User {
    s.mu.RLock()
    defer s.mu.RUnlock()

    users := make([]User, 0, len(s.byID))
    for _, user := range s.byID {
        users = append(users, user)
    }
    sort.Slice(users, func(i, j int) bool {
        if users[i].CreatedAt.Equal(users[j].CreatedAt) {
            return users[i].ID < users[j].ID
        }
        return users[i].CreatedAt.Before(users[j].CreatedAt)
    })
    return users
}

The PasswordHash field is tagged json:"-", so it can never be serialized into a response, even by accident. This is the same defensive idea as the unexported cause in APIError: make the dangerous thing impossible to emit instead of relying on every handler to remember not to.

newID now needs to produce IDs for more than one kind of thing. Give it a prefix parameter in store.go:

func newID(prefix string) (string, error) {
    b := make([]byte, 6)
    if _, err := rand.Read(b); err != nil {
        return "", err
    }
    return prefix + hex.EncodeToString(b), nil
}

and call it as newID("tsk_") inside Store.Create.

Session or JWT?

Once a user logs in, the client needs something to present on later requests. The two common choices are server-side sessions and signed tokens such as JWTs.

Opaque session token JWT (signed, self-contained)
Where the truth lives A server-side store Inside the token itself
Revoking a login Delete the session. Immediate Hard. The token is valid until it expires
Checking a request A store lookup Verify a signature, no lookup
Other services verifying it They must share the store They need only the key
Typical pitfalls The store becomes a dependency Algorithm confusion, long-lived stolen tokens, bloat

Forge is a single service, and revocation matters, because “log out” and “an administrator disabled this account” should take effect at once. So Forge uses opaque sessions. This is a decision about this system, not a verdict on JWTs. If several independent services later need to verify identity without sharing a store, signed tokens become the better trade, and Chapter 20’s discussion of boundaries returns to that.

package main

import (
    "crypto/rand"
    "crypto/sha256"
    "encoding/base64"
    "sync"
    "time"
)

type session struct {
    userID  string
    expires time.Time
}

type SessionStore struct {
    mu       sync.Mutex
    sessions map[[32]byte]session
    ttl      time.Duration
    now      func() time.Time
}

func NewSessionStore(ttl time.Duration) *SessionStore {
    return &SessionStore{sessions: make(map[[32]byte]session), ttl: ttl, now: time.Now}
}

func (s *SessionStore) Create(userID string) (string, time.Time, error) {
    b := make([]byte, 32)
    if _, err := rand.Read(b); err != nil {
        return "", time.Time{}, err
    }
    token := base64.RawURLEncoding.EncodeToString(b)
    expires := s.now().Add(s.ttl)

    s.mu.Lock()
    defer s.mu.Unlock()
    s.sessions[sha256.Sum256([]byte(token))] = session{userID: userID, expires: expires}
    return token, expires, nil
}

func (s *SessionStore) Lookup(token string) (string, bool) {
    key := sha256.Sum256([]byte(token))

    s.mu.Lock()
    defer s.mu.Unlock()

    sess, ok := s.sessions[key]
    if !ok {
        return "", false
    }
    if !s.now().Before(sess.expires) {
        delete(s.sessions, key)
        return "", false
    }
    return sess.userID, true
}

func (s *SessionStore) Revoke(token string) {
    s.mu.Lock()
    defer s.mu.Unlock()
    delete(s.sessions, sha256.Sum256([]byte(token)))
}

The token is 32 random bytes, far too many to guess. The store keeps only its SHA-256 hash. A fast hash is correct here, unlike for passwords, because the input is high-entropy random data and cannot be guessed offline. Looking sessions up by hash also means lookup timing reveals nothing about the token itself. The clock is an injectable now function so tests can move time without sleeping.

One cost is visible already: expired sessions that are never looked up again stay in the map forever. A real system needs a periodic sweep, which is a background job, and Chapter 25 builds that machinery.

Register, Login, Logout

New error shapes first. Add to errors.go:

func unauthenticated(message string) *APIError {
    return &APIError{Status: http.StatusUnauthorized, Code: "UNAUTHENTICATED", Message: message}
}

func forbidden(message string) *APIError {
    return &APIError{Status: http.StatusForbidden, Code: "FORBIDDEN", Message: message}
}

var errInvalidCredentials = &APIError{
    Status:  http.StatusUnauthorized,
    Code:    "INVALID_CREDENTIALS",
    Message: "email or password is incorrect",
}

and extend toAPIError with one more case, before the default:

case errors.Is(err, ErrEmailTaken):
    return conflict("ALREADY_EXISTS", "email already registered")

errInvalidCredentials is a shared package-level value, which would be a data race hazard if writeAPIError mutated it. It does not: Chapter 8 made writeAPIError copy the error before attaching a request ID, and this is the payoff.

Registration validates both fields and reports every problem at once, as Chapter 8 prescribed.

type credentials struct {
    Email    string `json:"email"`
    Password string `json:"password"`
}

func normalizeEmail(email string) string {
    return strings.ToLower(strings.TrimSpace(email))
}

func validateEmail(email string) *FieldError {
    if email == "" {
        return &FieldError{Field: "email", Code: "REQUIRED", Message: "email is required"}
    }
    addr, err := mail.ParseAddress(email)
    if err != nil || addr.Address != email || len(email) > 254 {
        return &FieldError{Field: "email", Code: "INVALID_VALUE", Message: "email must be a valid address"}
    }
    return nil
}

func validatePassword(password string) *FieldError {
    switch {
    case password == "":
        return &FieldError{Field: "password", Code: "REQUIRED", Message: "password is required"}
    case len(password) < minPasswordBytes:
        return &FieldError{Field: "password", Code: "TOO_SHORT", Message: fmt.Sprintf("password must be at least %d characters", minPasswordBytes)}
    case len(password) > maxPasswordBytes:
        return &FieldError{Field: "password", Code: "TOO_LONG", Message: fmt.Sprintf("password must be at most %d bytes", maxPasswordBytes)}
    }
    return nil
}

func (s *Server) register(w http.ResponseWriter, r *http.Request) error {
    var req credentials
    if err := decodeJSON(w, r, &req); err != nil {
        return err
    }

    email := normalizeEmail(req.Email)
    var problems []FieldError
    if p := validateEmail(email); p != nil {
        problems = append(problems, *p)
    }
    if p := validatePassword(req.Password); p != nil {
        problems = append(problems, *p)
    }
    if len(problems) > 0 {
        return invalidArgument("request validation failed", problems...)
    }

    hash, err := hashPassword(req.Password)
    if err != nil {
        return err
    }
    user, err := s.users.Create(email, hash, RoleMember)
    if err != nil {
        return err
    }

    writeJSON(w, http.StatusCreated, user)
    return nil
}

Registration deliberately leaves a hole open: a second registration with the same email returns a 409, which tells a stranger that the address has an account. Preventing that requires an email-verification flow, which is out of scope here, so we accept this leak and name it in the “still wrong” table below. Login is where it matters most, and there we close it.

type loginResponse struct {
    Token     string    `json:"token"`
    ExpiresAt time.Time `json:"expires_at"`
}

func (s *Server) login(w http.ResponseWriter, r *http.Request) error {
    var req credentials
    if err := decodeJSON(w, r, &req); err != nil {
        return err
    }

    user, lookupErr := s.users.GetByEmail(normalizeEmail(req.Email))
    hash := dummyHash()
    switch {
    case lookupErr == nil:
        hash = user.PasswordHash
    case !errors.Is(lookupErr, ErrUserNotFound):
        return lookupErr
    }

    // Always run the comparison, so a missing account takes as long as a wrong password.
    matchErr := bcrypt.CompareHashAndPassword(hash, []byte(req.Password))
    if lookupErr != nil || matchErr != nil {
        return errInvalidCredentials
    }

    token, expires, err := s.sessions.Create(user.ID)
    if err != nil {
        return err
    }

    w.Header().Set("Cache-Control", "no-store")
    writeJSON(w, http.StatusOK, loginResponse{Token: token, ExpiresAt: expires})
    return nil
}

Two behaviors here are about not leaking information. The response for an unknown email and for a wrong password is byte-for-byte the same, so an attacker cannot use login to discover which emails are registered. And the response time is the same too: if we skipped the slow bcrypt comparison for unknown emails, the faster response would reveal them just as clearly. The dummy hash exists to make the work identical on both paths. The Cache-Control: no-store header keeps the token out of any intermediary’s cache.

Logout needs the token again, and we read it with a small helper that also serves the middleware:

func bearerToken(r *http.Request) (string, bool) {
    scheme, token, found := strings.Cut(r.Header.Get("Authorization"), " ")
    token = strings.TrimSpace(token)
    if !found || !strings.EqualFold(scheme, "Bearer") || token == "" {
        return "", false
    }
    return token, true
}

func (s *Server) logout(w http.ResponseWriter, r *http.Request) error {
    if token, ok := bearerToken(r); ok {
        s.sessions.Revoke(token)
    }
    w.WriteHeader(http.StatusNoContent)
    return nil
}

The Authentication Middleware

Authentication happens once, in middleware, and the result travels in the request context, just like the request ID.

type Identity struct {
    UserID string
    Role   Role
}

type identityCtxKey struct{}

func identityFromContext(ctx context.Context) (Identity, bool) {
    id, ok := ctx.Value(identityCtxKey{}).(Identity)
    return id, ok
}

func writeUnauthenticated(w http.ResponseWriter, r *http.Request, logger *slog.Logger, message string) {
    w.Header().Set("WWW-Authenticate", "Bearer")
    writeAPIError(w, r, logger, unauthenticated(message))
}

func requireAuth(sessions *SessionStore, users *UserStore, logger *slog.Logger) middleware {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            token, ok := bearerToken(r)
            if !ok {
                writeUnauthenticated(w, r, logger, "missing or malformed Authorization header")
                return
            }
            userID, ok := sessions.Lookup(token)
            if !ok {
                writeUnauthenticated(w, r, logger, "invalid or expired token")
                return
            }
            user, err := users.GetByID(userID)
            if errors.Is(err, ErrUserNotFound) {
                writeUnauthenticated(w, r, logger, "invalid or expired token")
                return
            }
            if err != nil {
                writeAPIError(w, r, logger, err)
                return
            }

            ctx := context.WithValue(r.Context(), identityCtxKey{}, Identity{UserID: user.ID, Role: user.Role})
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}

The middleware loads the user on every request instead of caching the role in the session. That costs a lookup, and it means a role change or a deleted account takes effect on the very next request. Once users live in a database, that lookup will matter, and a short cache will be the trade to consider.

Handlers read the identity through a function that fails closed:

func requireIdentity(r *http.Request) (Identity, error) {
    id, ok := identityFromContext(r.Context())
    if !ok {
        return Identity{}, internalError(errors.New("handler requires authentication but none was applied"))
    }
    return id, nil
}

If a developer registers a route and forgets to wrap it in authentication, the handler does not quietly proceed as an anonymous user. It returns a 500 and logs the mistake. A missing security layer should produce a loud failure, never a silent open door.

A second small middleware handles role requirements, and it fails closed as well.

func requireRole(logger *slog.Logger, role Role) middleware {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            id, ok := identityFromContext(r.Context())
            if !ok || id.Role != role {
                writeAPIError(w, r, logger, forbidden("insufficient permissions"))
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}

Authorization: Ownership and Roles

Authentication tells us who the caller is. Now the tasks need owners. Add the field to Task:

OwnerID string `json:"owner_id"`

Store.Create takes the owner as its first argument and records it, and Store.List gains an owner filter:

func (s *Store) Create(ownerID, title string) (Task, error)

// List returns tasks in creation order. An empty ownerID returns every task.
func (s *Store) List(ownerID string) []Task

Inside List, the loop skips tasks whose owner does not match whenever ownerID is not empty. The empty-string-means-everything convention is a shortcut we will remove when a database lets us express the filter as a query.

The access rule is one small function, in one place:

func (i Identity) canAccess(t Task) bool {
    return i.Role == RoleAdmin || t.OwnerID == i.UserID
}

The handlers apply it after loading the task.

func (s *Server) getTask(w http.ResponseWriter, r *http.Request) error {
    identity, err := requireIdentity(r)
    if err != nil {
        return err
    }

    task, err := s.store.Get(r.PathValue("id"))
    if err != nil {
        return err
    }
    if !identity.canAccess(task) {
        return notFound("task not found")
    }

    writeJSON(w, http.StatusOK, task)
    return nil
}

transitionTask gets the same treatment: load the task, check access, and only then call Transition. createTask takes the owner from the identity, never from the request:

task, err := s.store.Create(identity.UserID, title)

And listTasks asks for the caller’s tasks only, unless the caller is an admin:

ownerID := identity.UserID
if identity.Role == RoleAdmin {
    ownerID = ""
}
writeJSON(w, http.StatusOK, s.store.List(ownerID))

Why 404 and not 403

When a member requests another member’s task, we answer 404, exactly as if the task did not exist. A 403 would confirm that the ID is real, which is a small leak, and it would let an attacker enumerate valid IDs by watching which ones are forbidden. The rule we adopt:

Situation Response Reason
The caller may not know the resource exists 404 Do not confirm existence
The caller knows the resource exists but may not perform this action 403 The refusal reveals nothing new

Listing all users is the second kind: every member knows the endpoint exists, so a member who calls GET /users gets a 403.

Immutable owners make checks safe

There is a subtle point in “load the task, check access, then act.” Between the check and the action, something could change. If it can change in a way that affects the answer, the check is worthless, which is the same check-then-act race from Chapter 1. Here it cannot: a task’s owner is set at creation and never changes, so access cannot be revoked between the two steps. An authorization decision based on an immutable attribute is race-free. A decision based on mutable state must be made atomically with the action. If we ever add “transfer ownership,” the design must be revisited.

Roles, permissions, and when to grow

Two roles with a hard-coded rule is the right size for Forge. As rules multiply, systems tend to move through a predictable sequence.

Model Shape Fits when
Role checks “Admins may do X” A few roles, few rules
Permissions Roles grant named permissions such as tasks:read_all Many rules, or rules that change without redeploying
Ownership and relationships “Members of this project may edit its tasks” Sharing between users
Policy engines Rules written in a dedicated policy language Many services need the same rules

Moving up the table is a response to pain. Moving early buys complexity with no benefit.

Wiring It Together

The server gains its two stores. Update Server and its constructor:

type Server struct {
    store    *Store
    users    *UserStore
    sessions *SessionStore
    logger   *slog.Logger
}

func NewServer(store *Store, users *UserStore, sessions *SessionStore, logger *slog.Logger) *Server {
    return &Server{store: store, users: users, sessions: sessions, logger: logger}
}

Routes now declare, in one visible place, which of them require authentication and which require a role:

func (s *Server) routes() http.Handler {
    auth := requireAuth(s.sessions, s.users, s.logger)
    admin := requireRole(s.logger, RoleAdmin)

    mux := http.NewServeMux()
    mux.HandleFunc("GET /health", s.handle(s.health))

    mux.HandleFunc("POST /auth/register", s.handle(s.register))
    mux.HandleFunc("POST /auth/login", s.handle(s.login))
    mux.Handle("POST /auth/logout", auth(s.handle(s.logout)))

    mux.Handle("GET /users/me", auth(s.handle(s.me)))
    mux.Handle("GET /users", auth(admin(s.handle(s.listUsers))))

    mux.Handle("POST /tasks", auth(s.handle(s.createTask)))
    mux.Handle("GET /tasks", auth(s.handle(s.listTasks)))
    mux.Handle("GET /tasks/{id}", auth(s.handle(s.getTask)))
    mux.Handle("POST /tasks/{id}/transition", auth(s.handle(s.transitionTask)))

    return chain(routerErrors(mux, s.logger), requestID, requestLogger(s.logger), recoverer(s.logger))
}

Note that authentication wraps individual routes, inside the global middleware chain. A request rejected as unauthenticated still receives a request ID and an access log line, and a panic inside authentication code is still recovered. The me and listUsers handlers follow the same shape as the others: take the identity, call a store, write JSON.

Finally, main seeds the first administrator. This is a placeholder for the configuration system of Chapter 37, and it keeps admin creation out of the API:

users := NewUserStore()
if email, password := os.Getenv("FORGE_ADMIN_EMAIL"), os.Getenv("FORGE_ADMIN_PASSWORD"); email != "" && password != "" {

        os.Exit(1)

Security Boundaries

A trust boundary is a line where data passes from something you do not control to something you do. Everything that crosses it must be treated as hostile until proven otherwise.

Input Trusted? How we handle it
Request body fields No Strict decoding and validation
Authorization header No Looked up, never interpreted
Owner or role claimed by the client Never Identity comes only from the verified session
The X-Request-ID header No Validated before it reaches the logs
Our own stores Yes, but fail closed Missing identity produces a 500, never access

One boundary deserves an example. Suppose a client sends {"title":"x","owner_id":"usr_someoneelse"}. Many frameworks bind every field they find to the object, which lets a client set properties it should never control, a flaw called mass assignment. Forge is immune, and the reason is a decision from Chapter 5: the decoder rejects unknown fields. owner_id is not part of createTaskRequest, so the request fails with a 400. A strict contract is also a security control.

Everything in this chapter assumes the connection is encrypted. A bearer token sent over plain HTTP is a password written on a postcard, so Forge must be served over TLS. Where TLS terminates is a deployment decision for Chapter 38.

Testing Security

The test environment grows to hold the stores, and bcrypt runs at its minimum cost so the suite stays fast.

func TestMain(m *testing.M) {

type testEnv struct {
    handler http.Handler
    users   *UserStore
}

func newTestEnv() *testEnv {
    logger := slog.New(slog.NewTextHandler(io.Discard, nil))

func sendAs(h http.Handler, token, method, path, contentType, body string) *httptest.ResponseRecorder {
    req := httptest.NewRequest(method, path, strings.NewReader(body))
    if contentType != "" {
        req.Header.Set("Content-Type", contentType)
    }
    if token != "" {
        req.Header.Set("Authorization", "Bearer "+token)
    }
    rec := httptest.NewRecorder()
    h.ServeHTTP(rec, req)
    return rec
}

func send(h http.Handler, method, path, contentType, body string) *httptest.ResponseRecorder {
    return sendAs(h, "", method, path, contentType, body)
}

func (e *testEnv) login(t *testing.T, email, password string) string {
    t.Helper()
    creds := fmt.Sprintf(`{"email":%q,"password":%q}`, email, password)

    rec := send(e.handler, http.MethodPost, "/auth/login", "application/json", creds)
    if rec.Code != http.StatusOK {
        t.Fatalf("login status = %d, body = %s", rec.Code, rec.Body)
    }
    var body loginResponse
    if err := json.NewDecoder(rec.Body).Decode(&body); err != nil {
        t.Fatalf("decode login response: %v", err)
    }
    return body.Token
}

func (e *testEnv) signUp(t *testing.T, email, password string) string {
    t.Helper()
    creds := fmt.Sprintf(`{"email":%q,"password":%q}`, email, password)

    rec := send(e.handler, http.MethodPost, "/auth/register", "application/json", creds)
    if rec.Code != http.StatusCreated {
        t.Fatalf("register status = %d, body = %s", rec.Code, rec.Body)
    }
    return e.login(t, email, password)
}

func (e *testEnv) addAdmin(t *testing.T, email, password string) {
    t.Helper()
    hash, err := hashPassword(password)
    if err != nil {
        t.Fatal(err)
    }
    if _, err := e.users.Create(email, hash, RoleAdmin); err != nil {
        t.Fatal(err)
    }
}

func TestAuthentication(t *testing.T) {
    env := newTestEnv()
    token := env.signUp(t, "ada@example.com", "correct horse")

    tests := []struct {
        name       string
        token      string
        wantStatus int
    }{
        {"no token", "", http.StatusUnauthorized},
        {"garbage token", "not-a-token", http.StatusUnauthorized},
        {"valid token", token, http.StatusOK},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            rec := sendAs(env.handler, tt.token, http.MethodGet, "/tasks", "", "")
            if rec.Code != tt.wantStatus {
                t.Fatalf("status = %d, want %d", rec.Code, tt.wantStatus)
            }
            if tt.wantStatus == http.StatusUnauthorized && rec.Header().Get("WWW-Authenticate") == "" {
                t.Fatal("401 response is missing WWW-Authenticate")
            }
        })
    }

    if rec := sendAs(env.handler, token, http.MethodPost, "/auth/logout", "", ""); rec.Code != http.StatusNoContent {
        t.Fatalf("logout status = %d, want %d", rec.Code, http.StatusNoContent)
    }
    if rec := sendAs(env.handler, token, http.MethodGet, "/tasks", "", ""); rec.Code != http.StatusUnauthorized {
        t.Fatalf("token still valid after logout: status = %d", rec.Code)
    }
}

func TestLoginDoesNotRevealWhichPartWasWrong(t *testing.T) {
    env := newTestEnv()
    env.signUp(t, "ada@example.com", "correct horse")

    attempt := func(email, password string) (int, string, string) {
        creds := fmt.Sprintf(`{"email":%q,"password":%q}`, email, password)
        rec := send(env.handler, http.MethodPost, "/auth/login", "application/json", creds)

        var body testErrorBody
        if err := json.NewDecoder(rec.Body).Decode(&body); err != nil {
            t.Fatalf("decode: %v", err)
        }
        return rec.Code, body.Error.Code, body.Error.Message
    }

    s1, c1, m1 := attempt("ada@example.com", "wrong password")
    s2, c2, m2 := attempt("nobody@example.com", "wrong password")

    if s1 != http.StatusUnauthorized || s1 != s2 || c1 != c2 || m1 != m2 {
        t.Fatalf("responses differ: (%d %s %q) vs (%d %s %q)", s1, c1, m1, s2, c2, m2)
    }
}

func TestTaskOwnership(t *testing.T) {
    env := newTestEnv()
    env.addAdmin(t, "root@example.com", "admin password")
    ada := env.signUp(t, "ada@example.com", "correct horse")
    bob := env.signUp(t, "bob@example.com", "battery staple")
    admin := env.login(t, "root@example.com", "admin password")
    const jsonType = "application/json"

    rec := sendAs(env.handler, ada, http.MethodPost, "/tasks", jsonType, `{"title":"Ada's task"}`)
    if rec.Code != http.StatusCreated {
        t.Fatalf("create status = %d, body = %s", rec.Code, rec.Body)
    }
    var created Task
    if err := json.NewDecoder(rec.Body).Decode(&created); err != nil {
        t.Fatalf("decode: %v", err)
    }
    path := "/tasks/" + created.ID

    tests := []struct {
        name       string
        token      string
        method     string
        path       string
        body       string
        wantStatus int
    }{
        {"owner reads", ada, http.MethodGet, path, "", http.StatusOK},
        {"other member reads", bob, http.MethodGet, path, "", http.StatusNotFound},
        {"other member transitions", bob, http.MethodPost, path + "/transition", `{"to":"running"}`, http.StatusNotFound},
        {"admin reads", admin, http.MethodGet, path, "", http.StatusOK},
        {"owner transitions", ada, http.MethodPost, path + "/transition", `{"to":"running"}`, http.StatusOK},
        {"cannot assign an owner", bob, http.MethodPost, "/tasks", `{"title":"x","owner_id":"` + created.OwnerID + `"}`, http.StatusBadRequest},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {

            if rec.Code != tt.wantStatus {
                t.Fatalf("status = %d, want %d, body = %s", rec.Code, tt.wantStatus, rec.Body)
            }
        })
    }
}

func TestSessionExpiry(t *testing.T) {
    now := time.Date(2026, 10, 3, 9, 0, 0, 0, time.UTC)
    sessions := NewSessionStore(time.Hour)
    sessions.now = func() time.Time { return now }

    token, _, err := sessions.Create("usr_1")
    if err != nil {
        t.Fatal(err)
    }
    if _, ok := sessions.Lookup(token); !ok {
        t.Fatal("a fresh session should be valid")
    }

    now = now.Add(time.Hour)
    if _, ok := sessions.Lookup(token); ok {
        t.Fatal("an expired session should be rejected")
    }
}

Engineering Lens

What problem did we solve? We gave the system a notion of identity, tied every task to an owner, and made access decisions in one small, testable place, without changing the shape of any handler beyond reading the identity.

What complexity did we introduce? Two new stores, a new dependency, two middlewares, and the discipline that every route must declare its authentication. Security is now a property of the route table.

What failure modes appeared? Information leaks through timing and error messages, mass assignment, forgotten authentication on a new route, stolen tokens, and brute-force guessing. Each has either a control in this chapter or a named chapter that supplies one.

What would break at 10× scale? The per-request user lookup, the single process-wide session store that a second instance would not share, and bcrypt’s deliberate CPU cost, which an attacker can use to saturate login endpoints.

When should we not build our own authentication? Often. Many teams are better served by an identity provider that handles passwords, verification, reset, and multi-factor authentication. Building it is a reasonable way to understand it. Operating it forever is a separate commitment, and the security surface is large.

  1. Remove the dummy-hash comparison from login and time a login for a missing user versus a wrong password, using many repetitions. How large is the difference, and could an attacker measure it over a network?
  2. Add a new route and forget to wrap it in auth. What happens when a handler calls requireIdentity? Why is that better than the handler silently treating the caller as anonymous?
  3. Temporarily change the 404 for a foreign task to a 403. What can a member now learn about other members’ tasks? Write the enumeration attack in two sentences.
  4. Design, without implementing, a “share this task with another user” feature. Which of the four authorization models in this chapter does it require, and which immutable-attribute argument stops working?

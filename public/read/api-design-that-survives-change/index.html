Chapter 10: API Design That Survives Change

By Abir Sarkar · 21 min read · Published 2026-10-03 · LinkedIn

Until now Forge has had no users but us, so every change was free. We renamed things, tightened rules, and broke the contract whenever the design improved, and the only cost was updating our own tests. That luxury ends the day someone else writes code against the API. From that moment, every decision becomes a promise, and promises are expensive to break.

This chapter is about making the promises you can keep, and about the small number of changes that are still cheap now. Forge has no outside clients yet, which makes this the last moment those changes cost almost nothing. We will use it.

Why APIs Are Hard to Change

An API has two kinds of readers: the clients that call it and the people who write them. You can control the code you ship. You cannot control the code written against it, and you often cannot even find it. There is a well-known observation that with enough users, every observable behavior of your system will be depended on by somebody, including behavior you never meant to promise. A response that happened to be sorted, a field that happened to be present, an error message that happened to contain a word: all of them become contract by use.

The practical response is to decide deliberately which behaviors are promises, document them, and change everything else freely.

What Counts as a Breaking Change

Not every change breaks clients. The table sorts the common ones.

Change Safe for existing clients? Notes
Add an optional request field Yes Old clients simply do not send it
Add a field to a response Usually Safe only if clients ignore fields they do not know
Add a new endpoint Yes
Add a new value to a response enum, such as a new task status Risky Clients that switch over the values may break
Add a required request field No Existing requests become invalid
Rename or remove a field No
Change a field’s type or format No
Tighten validation No Chapter 5’s Content-Type change broke every curl command
Loosen validation Usually
Change a default page size or ordering No, in practice Someone depends on it
Change an error code or the status for a situation No Clients branch on them

The second row hides an obligation. Forge is strict about requests: it rejects unknown fields. But for responses, clients must be tolerant: they must ignore fields they do not recognize. The two rules are complementary, and the API documentation has to state the second one explicitly, because without it we could never add a response field safely.

Naming and Resource Modeling

Conventions look trivial and matter enormously, because inconsistency forces every client to special-case. Forge adopts these, and every endpoint obeys all of them.

Convention Rule Example
Resources Plural nouns /tasks, /users
Identifiers Opaque strings with a type prefix tsk_8f3a1c9d2b47
JSON fields lower_snake_case created_at, owner_id
Timestamps RFC 3339, always UTC 2026-10-03T09:14:00Z
Enumerations Lowercase strings "pending", "running"
Nesting At most two levels /tasks/{id}/transition
State changes A named action on the resource POST /tasks/{id}/transition

The last row records a decision from Chapter 6 that deserves its justification. The alternative design, PATCH /tasks/{id} with a status field, treats a status change as an ordinary field edit. But a status change is not an edit. It is a transition governed by rules, with a conflict policy. Giving it its own endpoint keeps the rules visible in the contract and prevents a client from sending a patch that rewrites status along with five unrelated fields.

Pagination: Never Return Everything

Chapter 4 flagged GET /tasks: it returns every task, and one million tasks produce a million-element response. Bounded results are not an optimization. They are part of the contract.

There are two common designs.

Offset pagination Cursor pagination
Request ?offset=40&limit=20 ?cursor=<opaque>&limit=20
Jump to page N Easy Not possible
Stable when rows are added or removed No. Items shift, so pages repeat or skip rows Yes. The cursor marks a position, not a count
Cost on a large table Grows with the offset, because skipped rows are still read Constant, since a cursor seeks directly
Simplicity Very simple Slightly more work

Forge uses cursors. Users read task lists from the top and move forward, which is exactly the access pattern cursors serve well, and the stability matters because tasks are being created while people page through them.

The cursor is a position

A cursor records “the last item you saw,” expressed in the sort order: here, creation time with the ID as a tie-breaker. The next page is everything strictly after that position.

type cursor struct {
    CreatedAt time.Time `json:"t"`
    ID        string    `json:"id"`
}

func encodeCursor(c cursor) (string, error) {
    b, err := json.Marshal(c)
    if err != nil {
        return "", err
    }
    return base64.RawURLEncoding.EncodeToString(b), nil
}

func decodeCursor(s string) (cursor, error) {
    b, err := base64.RawURLEncoding.DecodeString(s)
    if err != nil {
        return cursor{}, err
    }
    var c cursor
    if err := json.Unmarshal(b, &c); err != nil {
        return cursor{}, err
    }
    if c.ID == "" || c.CreatedAt.IsZero() {
        return cursor{}, errors.New("incomplete cursor")
    }
    return c, nil
}

The client sees a meaningless string. Opacity is the point: because clients cannot interpret the cursor, we can change what it encodes without breaking anyone. A cursor that exposed ?after_id=... would have turned an implementation detail into a promise. The cursor encodes only a position, never anything about permissions, so a tampered cursor can at worst point somewhere else in the caller’s own results, because the owner filter is applied separately on the server.

The store and the query

The store’s listing function takes a parameter struct, because the number of options will keep growing.

type ListParams struct {
    OwnerID string  // empty means every owner
    Status  Status  // empty means every status
    After   *cursor // nil means from the start
    Limit   int
}

func taskLess(a, b Task) bool {
    if a.CreatedAt.Equal(b.CreatedAt) {
        return a.ID < b.ID
    }
    return a.CreatedAt.Before(b.CreatedAt)
}

func taskAfter(t Task, c cursor) bool {
    if t.CreatedAt.Equal(c.CreatedAt) {
        return t.ID > c.ID
    }
    return t.CreatedAt.After(c.CreatedAt)
}

func (s *Store) List(p ListParams) ([]Task, bool) {
    s.mu.RLock()
    defer s.mu.RUnlock()

    all := make([]Task, 0, len(s.tasks))
    for _, task := range s.tasks {
        if p.OwnerID != "" && task.OwnerID != p.OwnerID {
            continue
        }
        if p.Status != "" && task.Status != p.Status {
            continue
        }
        if p.After != nil && !taskAfter(task, *p.After) {
            continue
        }
        all = append(all, task)
    }
    sort.Slice(all, func(i, j int) bool { return taskLess(all[i], all[j]) })

    if len(all) > p.Limit {
        return all[:p.Limit], true
    }
    return all, false
}

The function returns the page and a flag saying whether more results exist. Finding out whether there is a next page without an extra query is a common trick: fetch one more than you need. Here we have everything in memory and simply compare lengths. When the store becomes a database in Part III, this becomes a seek, not a scan:

SELECT ... WHERE owner_id = $1 AND (created_at, id) > ($2, $3)
ORDER BY created_at, id LIMIT $4

One honest limitation remains. Keyset pagination is only as stable as its sort key. Breaking ties by ID guarantees pages never repeat or loop, but a row created with a timestamp at or before the cursor’s position can be missed, which is possible when two rows share a timestamp and the later one has the smaller random ID. Real systems answer this with a strictly increasing key such as a sequence number, or they accept the edge case. The lesson is general: a pagination scheme is a promise about ordering, and you should know exactly what yours promises.

Parsing the query

Query parameters are input like any other, and they get the same validation and the same error contract.

const (
    defaultPageSize = 20
    maxPageSize     = 100
)

type taskPage struct {
    Items      []Task `json:"items"`
    NextCursor string `json:"next_cursor,omitempty"`
}

func parseListParams(r *http.Request, identity Identity) (ListParams, error) {
    q := r.URL.Query()
    p := ListParams{Limit: defaultPageSize}
    var problems []FieldError

    if raw := q.Get("limit"); raw != "" {
        n, err := strconv.Atoi(raw)
        if err != nil || n < 1 || n > maxPageSize {
            problems = append(problems, FieldError{
                Field: "limit", Code: "INVALID_VALUE",
                Message: fmt.Sprintf("limit must be an integer between 1 and %d", maxPageSize),
            })
        } else {
            p.Limit = n
        }
    }
    if raw := q.Get("status"); raw != "" {
        if status := Status(raw); !status.Valid() {
            problems = append(problems, FieldError{Field: "status", Code: "INVALID_VALUE", Message: "status must be a valid status"})
        } else {
            p.Status = status
        }
    }
    if raw := q.Get("cursor"); raw != "" {
        c, err := decodeCursor(raw)
        if err != nil {
            problems = append(problems, FieldError{Field: "cursor", Code: "INVALID_VALUE", Message: "cursor is not valid"})
        } else {
            p.After = &c
        }
    }
    if len(problems) > 0 {
        return ListParams{}, invalidArgument("request validation failed", problems...)
    }

    if identity.Role != RoleAdmin {
        p.OwnerID = identity.UserID
    }
    return p, nil
}

func (s *Server) listTasks(w http.ResponseWriter, r *http.Request) error {
    identity, err := requireIdentity(r)
    if err != nil {
        return err
    }
    params, err := parseListParams(r, identity)
    if err != nil {
        return err
    }

    tasks, hasMore := s.store.List(params)
    page := taskPage{Items: tasks}
    if hasMore {
        last := tasks[len(tasks)-1]
        next, err := encodeCursor(cursor{CreatedAt: last.CreatedAt, ID: last.ID})
        if err != nil {
            return err
        }
        page.NextCursor = next
    }

    writeJSON(w, http.StatusOK, page)
    return nil
}

Two decisions are visible. The page has a default and a maximum, so a client that asks for nothing gets a sensible answer and a client that asks for everything is refused. And unlike request bodies, unknown query parameters are ignored, because intermediaries and analytics tools routinely append parameters of their own, and rejecting them would break legitimate traffic.

The envelope, and why we break the contract now

Notice the response shape. Chapter 3’s contract said GET /tasks returns a list. The new response is an object with items and next_cursor. That is a breaking change, and we make it on purpose.

A bare JSON array is a design you cannot extend. There is nowhere to put a next_cursor, a total count, or a warning, and adding any of them later would be a breaking change of the same size as the one we are making now. An object can grow forever by adding fields. Because Forge has no outside clients, the change costs us a few test updates. It would cost far more after release. This is the broader lesson of the chapter: the best time to fix a contract is before anyone depends on it, and the second-best time is never.

Filtering and sorting, restrained

We support one filter, status, and one order, creation time ascending. Every option a client can send is a permanent promise, and it multiplies against every other option. Arbitrary sorting, for instance, would require the cursor to encode the sort key, and filtering across pages requires the client to repeat the same filter on every request, because the cursor remembers a position, not a query. Add features when a real client needs them, not because they are cheap to write.

Versioning

Even with great care, some changes break clients, and a version gives them somewhere to go. The common mechanisms are compared below.

Mechanism Example Trade-off
Version in the path /v1/tasks Obvious, easy to route and to see in logs. Changes URLs
Version in a header X-API-Version: 1 Clean URLs, but invisible and easy to forget
Version in the media type Accept: application/vnd.forge.v1+json Principled, awkward in practice
Version in a query parameter ?version=1 Easy, easily dropped by caches and proxies

Forge uses the path. It is the most visible option, and visibility is what you want from a version. We adopt it now, while it costs a global find-and-replace. Everything the API serves moves under /v1, except /health, which is for infrastructure and not for clients. Every route in routes() gains the prefix, the Location header becomes /v1/tasks/..., and every test path follows. Notice how many places that touches. Had we waited for clients, each of them would have been a place too.

A version number is not a licence to break things casually. The policy is:

Rule Detail
Additive changes stay within a version New fields, endpoints, and optional parameters do not require v2
A breaking change creates a new version v2 runs alongside v1, so clients move on their own schedule
Old versions are retired with notice A Sunset header announces the date, and a Deprecation header marks the endpoint

Idempotency: Safe Retries

Chapter 5 left a problem open. A client whose request timed out cannot know whether it took effect, so it retries, and POST /tasks creates a duplicate. Chapter 6 found a second symptom: a retried transition returns a 409 even though the first attempt succeeded. Both come from the same gap. The server cannot tell a new request from a repeat of an earlier one.

The fix is for the client to label its intent. The client generates a unique value and sends it as an Idempotency-Key header. If the server sees the same key again, it recognizes the repeat and returns the original result instead of acting twice.

This is different from the request ID from Chapter 7, and the difference is worth stating precisely.

Request ID Idempotency key
Assigned by The server (or accepted from a caller) The client
Identifies One HTTP attempt One intended operation, across all its retries
Changes on retry Yes, each attempt differs No, that is the whole point
Used for Debugging and log correlation Preventing duplicate effects

The rules

Situation Response
New key Process the request and remember a successful result
Same key, same request, finished Replay the stored response, marked Idempotent-Replayed: true
Same key, different request 409 IDEMPOTENCY_KEY_REUSED, because the client is misusing the key
Same key, first request still running 409 IDEMPOTENCY_KEY_IN_PROGRESS with Retry-After
No key Behave as before. The header is optional

Keys are scoped to the authenticated user, so one user’s keys can never collide with another’s. Only successful responses are stored. Idempotency exists to protect effects, and a failed request had none, so a retry of a failed request should simply run again and produce a fresh answer. A request is “the same” when its method, URL, and body are identical, which we check with a hash.

package main

import (
    "bytes"
    "crypto/sha256"
    "errors"
    "io"
    "log/slog"
    "net/http"
    "sync"
    "time"
)

type idempotencyResult int

const (
    idempotencyNew idempotencyResult = iota
    idempotencyReplay
    idempotencyMismatch
    idempotencyInFlight
)

type idempotencyEntry struct {
    fingerprint [32]byte
    done        bool
    status      int
    contentType string
    location    string
    body        []byte
    expires     time.Time
}

type IdempotencyStore struct {
    mu      sync.Mutex
    entries map[string]idempotencyEntry
    ttl     time.Duration
    now     func() time.Time
}

func NewIdempotencyStore(ttl time.Duration) *IdempotencyStore {
    return &IdempotencyStore{entries: make(map[string]idempotencyEntry), ttl: ttl, now: time.Now}
}

func (s *IdempotencyStore) Begin(id string, fp [32]byte) (idempotencyResult, idempotencyEntry) {
    s.mu.Lock()
    defer s.mu.Unlock()

    entry, ok := s.entries[id]
    if ok && !s.now().Before(entry.expires) {
        delete(s.entries, id)
        ok = false
    }

    switch {
    case !ok:
        s.entries[id] = idempotencyEntry{fingerprint: fp, expires: s.now().Add(s.ttl)}
        return idempotencyNew, idempotencyEntry{}
    case entry.fingerprint != fp:
        return idempotencyMismatch, idempotencyEntry{}
    case !entry.done:
        return idempotencyInFlight, idempotencyEntry{}
    default:
        return idempotencyReplay, entry
    }
}

func (s *IdempotencyStore) Complete(id string, status int, contentType, location string, body []byte) {
    s.mu.Lock()
    defer s.mu.Unlock()

    entry, ok := s.entries[id]
    if !ok {
        return
    }
    entry.done = true
    entry.status = status
    entry.contentType = contentType
    entry.location = location
    entry.body = body
    s.entries[id] = entry
}

func (s *IdempotencyStore) Abandon(id string) {
    s.mu.Lock()
    defer s.mu.Unlock()
    delete(s.entries, id)
}

The store’s Begin is where the whole guarantee lives. It checks and records under a single lock, so when twenty identical requests arrive at once, exactly one is told it is new and the other nineteen are told it is in flight or a replay. This is the Chapter 6 atomic check-and-write, applied to a new problem.

The middleware wraps a handler. It needs to capture what the handler wrote so it can store it, so it uses a writer that records the body as well as the status, built on the responseRecorder from Chapter 7.

type captureWriter struct {
    *responseRecorder
    body bytes.Buffer
}

func (c *captureWriter) Write(b []byte) (int, error) {
    c.body.Write(b)
    return c.responseRecorder.Write(b)
}

func idempotent(store *IdempotencyStore, logger *slog.Logger) middleware {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            key := r.Header.Get("Idempotency-Key")
            if key == "" {
                next.ServeHTTP(w, r)
                return
            }
            // Keys follow the same character rules as request IDs.
            if !validRequestID(key) {
                writeAPIError(w, r, logger, invalidArgument("request validation failed", FieldError{
                    Field:   "Idempotency-Key",
                    Code:    "INVALID_VALUE",
                    Message: "Idempotency-Key must be 1 to 64 letters, digits, hyphens, or underscores",
                }))
                return
            }

            identity, ok := identityFromContext(r.Context())
            if !ok {
                writeAPIError(w, r, logger, internalError(errors.New("idempotency requires authentication")))
                return
            }

            r.Body = http.MaxBytesReader(w, r.Body, maxBodyBytes)
            body, err := io.ReadAll(r.Body)
            if err != nil {
                writeAPIError(w, r, logger, decodeError(err))
                return
            }
            r.Body = io.NopCloser(bytes.NewReader(body))

            fingerprint := sha256.Sum256([]byte(r.Method + "\n" + r.URL.RequestURI() + "\n" + string(body)))
            id := identity.UserID + ":" + key

            result, entry := store.Begin(id, fingerprint)
            switch result {
            case idempotencyReplay:
                if entry.contentType != "" {
                    w.Header().Set("Content-Type", entry.contentType)
                }
                if entry.location != "" {
                    w.Header().Set("Location", entry.location)
                }
                w.Header().Set("Idempotent-Replayed", "true")
                w.WriteHeader(entry.status)
                if _, err := w.Write(entry.body); err != nil {
                    logger.WarnContext(r.Context(), "write replayed response", slog.Any("error", err))
                }
                return
            case idempotencyMismatch:
                writeAPIError(w, r, logger, conflict("IDEMPOTENCY_KEY_REUSED", "this Idempotency-Key was already used with a different request"))
                return
            case idempotencyInFlight:
                w.Header().Set("Retry-After", "1")
                writeAPIError(w, r, logger, conflict("IDEMPOTENCY_KEY_IN_PROGRESS", "a request with this Idempotency-Key is still being processed"))
                return
            }

            completed := false
            defer func() {
                if !completed {
                    store.Abandon(id)
                }
            }()

            cw := &captureWriter{responseRecorder: &responseRecorder{ResponseWriter: w, status: http.StatusOK}}
            next.ServeHTTP(cw, r)

            if cw.status < http.StatusOK || cw.status >= http.StatusMultipleChoices {
                return
            }
            store.Complete(id, cw.status, w.Header().Get("Content-Type"), w.Header().Get("Location"), cw.body.Bytes())
            completed = true
        })
    }
}

The defer is the quiet hero. If the handler panics, or returns anything other than a success, the deferred function removes the in-flight entry, so a failed first attempt can never leave a key stuck in the “in progress” state. That is the book’s namesake pattern guarding an invariant: whatever path the function takes out, the cleanup runs.

The middleware goes on the two endpoints with side effects that clients will want to retry, after authentication because it needs the identity:

mux.Handle("POST /v1/tasks", auth(idem(s.handle(s.createTask))))
mux.Handle("POST /v1/tasks/{id}/transition", auth(idem(s.handle(s.transitionTask))))

The key is optional. Making it mandatory would be safer, since the unsafe default is the one every careless client will use, but it would also break simple clients and curl commands. We choose compatibility, document the header prominently, and note the stricter alternative for services where duplicates are costly. The server gets one more dependency in its constructor, NewServer(store, users, sessions, idempotency, logger), and the number of parameters is by now a complaint worth listening to. Chapter 17 addresses it.

func (s *Server) routes() http.Handler {
    auth := requireAuth(s.sessions, s.users, s.logger)

    idem := idempotent(s.idempotency, s.logger)

Testing the Contract

Pagination is the easiest place to write a convincing test, because the property is clear: walking every page must yield exactly the same tasks, in the same order, as one large request, with nothing repeated and nothing dropped.

func TestPagination(t *testing.T) {
    env := newTestEnv()
    token := env.signUp(t, "ada@example.com", "correct horse")
    for i := 0; i < 5; i++ {
        body := fmt.Sprintf(`{"title":"task %d"}`, i)
        if rec := sendAs(env.handler, token, http.MethodPost, "/v1/tasks", "application/json", body); rec.Code != http.StatusCreated {
            t.Fatalf("create status = %d", rec.Code)
        }
    }

    fetch := func(query string) taskPage {
        t.Helper()
        rec := sendAs(env.handler, token, http.MethodGet, "/v1/tasks"+query, "", "")
        if rec.Code != http.StatusOK {
            t.Fatalf("status = %d, body = %s", rec.Code, rec.Body)
        }
        var page taskPage
        if err := json.NewDecoder(rec.Body).Decode(&page); err != nil {
            t.Fatalf("decode: %v", err)
        }
        return page
    }

    want := fetch("?limit=100")
    if len(want.Items) != 5 || want.NextCursor != "" {
        t.Fatalf("single page: %d items, next cursor %q", len(want.Items), want.NextCursor)
    }

    var got []Task
    query := "?limit=2"
    pages := 0
    for {
        page := fetch(query)
        pages++
        got = append(got, page.Items...)
        if page.NextCursor == "" {
            break
        }
        if pages > 10 {
            t.Fatal("pagination did not terminate")
        }
        query = "?limit=2&cursor=" + url.QueryEscape(page.NextCursor)
    }

    if pages != 3 {
        t.Fatalf("pages = %d, want 3", pages)
    }
    if len(got) != len(want.Items) {
        t.Fatalf("paged items = %d, want %d", len(got), len(want.Items))
    }
    for i := range got {
        if got[i].ID != want.Items[i].ID {
            t.Fatalf("item %d = %s, want %s", i, got[i].ID, want.Items[i].ID)
        }
    }
}

Idempotency needs a test for each row of the rules table, and one for the concurrent case, which is the one that justifies the whole design.

func TestIdempotentCreate(t *testing.T) {
    env := newTestEnv()
    token := env.signUp(t, "ada@example.com", "correct horse")

    post := func(key, body string) *httptest.ResponseRecorder {
        req := httptest.NewRequest(http.MethodPost, "/v1/tasks", strings.NewReader(body))
        req.Header.Set("Content-Type", "application/json")
        req.Header.Set("Authorization", "Bearer "+token)
        if key != "" {
            req.Header.Set("Idempotency-Key", key)
        }
        rec := httptest.NewRecorder()
        env.handler.ServeHTTP(rec, req)
        return rec
    }
    countTasks := func() int {
        rec := sendAs(env.handler, token, http.MethodGet, "/v1/tasks?limit=100", "", "")
        var page taskPage
        if err := json.NewDecoder(rec.Body).Decode(&page); err != nil {
            t.Fatalf("decode: %v", err)
        }
        return len(page.Items)
    }

    first := post("key-1", `{"title":"Write chapter one"}`)
    if first.Code != http.StatusCreated {
        t.Fatalf("first status = %d", first.Code)
    }

    replay := post("key-1", `{"title":"Write chapter one"}`)
    if replay.Code != http.StatusCreated || replay.Header().Get("Idempotent-Replayed") != "true" {
        t.Fatalf("replay: status = %d, replayed = %q", replay.Code, replay.Header().Get("Idempotent-Replayed"))
    }
    if replay.Body.String() != first.Body.String() {
        t.Fatalf("replayed body differs:\n%s\n%s", replay.Body, first.Body)
    }
    if replay.Header().Get("Location") != first.Header().Get("Location") {
        t.Fatal("replayed Location header differs")
    }
    if got := countTasks(); got != 1 {
        t.Fatalf("tasks after replay = %d, want 1", got)
    }

    if rec := post("key-1", `{"title":"A different task"}`); rec.Code != http.StatusConflict {
        t.Fatalf("reused key status = %d, want %d", rec.Code, http.StatusConflict)
    }

    post("", `{"title":"No key"}`)
    post("", `{"title":"No key"}`)
    if got := countTasks(); got != 3 {
        t.Fatalf("tasks without keys = %d, want 3 in total", got)
    }
}

func TestIdempotentCreateIsAtomicUnderConcurrency(t *testing.T) {
    env := newTestEnv()
    token := env.signUp(t, "ada@example.com", "correct horse")

    const attempts = 20
    var wg sync.WaitGroup
    for i := 0; i < attempts; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            req := httptest.NewRequest(http.MethodPost, "/v1/tasks", strings.NewReader(`{"title":"race"}`))
            req.Header.Set("Content-Type", "application/json")
            req.Header.Set("Authorization", "Bearer "+token)
            req.Header.Set("Idempotency-Key", "same-key")
            env.handler.ServeHTTP(httptest.NewRecorder(), req)
        }()
    }
    wg.Wait()

    rec := sendAs(env.handler, token, http.MethodGet, "/v1/tasks?limit=100", "", "")
    var page taskPage
    if err := json.NewDecoder(rec.Body).Decode(&page); err != nil {
        t.Fatalf("decode: %v", err)
    }
    if len(page.Items) != 1 {
        t.Fatalf("%d concurrent requests with one key created %d tasks, want 1", attempts, len(page.Items))
    }
}

The last test is the proof. Twenty identical requests race, and exactly one task exists afterward. Run it repeatedly with -race.

The Contract, Published

Part II ends with the contract in one place, which is what a client developer would actually read. First the endpoints.

Method and path Auth Idempotency key Purpose
GET /health None n/a Process liveness
POST /v1/auth/register None No Create an account
POST /v1/auth/login None No Exchange credentials for a session token
POST /v1/auth/logout Session No Revoke the session
GET /v1/users/me Session n/a The caller’s own profile

And the complete catalog of error codes, the one Chapter 8 promised and could not yet write. Codes are added over time, never renamed or reused.

Code Status Meaning
INVALID_ARGUMENT 400 Malformed request or failed validation, with details
UNAUTHENTICATED 401 Missing, invalid, or expired token
INVALID_CREDENTIALS 401 Wrong email or password
FORBIDDEN 403 Authenticated, but not permitted
NOT_FOUND 404 Resource or route does not exist, or is not visible to the caller
METHOD_NOT_ALLOWED 405 The path exists, but not for this method
ALREADY_EXISTS 409 A unique value is already taken
INVALID_TRANSITION 409 The status change is not allowed from the current state
IDEMPOTENCY_KEY_REUSED 409 The key was used with a different request
IDEMPOTENCY_KEY_IN_PROGRESS 409 The first request with this key is still running
PAYLOAD_TOO_LARGE 413 The body exceeds the size limit
UNSUPPORTED_MEDIA_TYPE 415 The body is not JSON
INTERNAL 500 An unexpected failure, with no detail exposed

Finally, the three rules of the contract: clients must ignore unknown fields in responses, must treat unknown error codes as a generic failure of their HTTP status category, and must treat cursors as opaque strings.

Engineering Lens

What problem did we solve? We made the API safe to depend on: bounded responses, an extensible envelope, a version, consistent conventions, and a way for clients to retry without duplicating effects.

What complexity did we introduce? Cursor encoding, an idempotency store with its own lifecycle, and a more disciplined contract that now constrains us as much as it protects clients.

What failure modes appeared? Missed rows from timestamp ties, stuck idempotency keys after a failure, a key reused with a different request, and clients that depend on behavior we never promised.

What would break at 10× scale? The idempotency and session stores, both held in one process’s memory. A second instance would not see the first’s keys, and a client’s retry could land on a different instance and create a duplicate. Shared state moves to a shared store.

When should we not build this much contract? For an internal API consumed by one team that deploys in lockstep with you, versioning and idempotency keys are overhead. The cost of a contract is justified by the number of callers you cannot coordinate with.

Exercises

  1. Walk Forge’s API with curl: register, log in, create a task with an Idempotency-Key, repeat the exact request, and compare the two responses. Then reuse the key with a different title. Explain each response in terms of the rules table.
  2. Write down three changes you might want to make to the API and classify each as breaking or safe using this chapter’s table. For each breaking one, describe what a v2 coexisting with v1 would require.
  3. Create two tasks with exactly the same created_at by constructing them directly in a store test. Page through them with limit=1. Does anything repeat or go missing? Explain what the ID tie-breaker guarantees and what it does not.
  4. The idempotency middleware stores only successful responses. Describe a scenario where storing a failure would be the better design, and what the client would then need to do to retry intentionally.
  5. Make Idempotency-Key mandatory on POST /v1/tasks. List every consequence for existing tests and clients, and decide whether the added safety is worth it for Forge.

What Part II Gave You

Six chapters ago, Forge was a handler that wrote JSON. It is now an API you could hand to a stranger: a protocol you understand down to the bytes, handlers with one job, middleware that gives every request an identity and a record, a contract for failure, a way to know who is asking, and a design that can grow without breaking its callers.

It also has a flaw that every chapter in this part has quietly pointed at. Look at everything Forge remembers: tasks, users, sessions, and idempotency keys. All of it lives in the memory of one process.

State What a restart destroys
Tasks The only copy of the user’s work
Users Every account. Nobody can ever log in again
Sessions Every login. Inconvenient, and recoverable by logging in again
Idempotency keys Retry protection. Briefly dangerous, then harmless

These four kinds of state need four different levels of care, and they are not all equally precious. Part III begins with the question that sorts them: where does state actually live, and which copy is the truth?

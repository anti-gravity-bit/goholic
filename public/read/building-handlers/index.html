Chapter 6: Building Handlers

By Abir Sarkar · 12 min read · Published 2026-10-03 · LinkedIn

Handlers begin small and grow like weeds. The createTask handler from Chapter 4 was twenty lines. It looked fine because it did very little. This chapter gives Forge a more demanding job, lets the handler absorb all of it, and then looks honestly at what we built.

The teaching pattern here recurs for the rest of the book: first make the problem visible, then introduce the abstraction that solves it. An abstraction offered before its problem is just vocabulary.

The New Requirement

Chapter 3 defined a lifecycle for tasks, with five states and a table of allowed transitions. Until now nothing could change a task’s status. Forge needs an endpoint that does.

We choose a single action endpoint:

POST /tasks/{id}/transition
{ "to": "running" }

It is a POST because it changes state and is not idempotent in the HTTP sense. The success response is the updated task. The failure cases come straight from Chapter 3.

Situation Response
Body malformed, or to is not a known status 400 INVALID_ARGUMENT
Task does not exist 404 NOT_FOUND
Transition is not allowed from the current status 409 INVALID_TRANSITION
Two callers race for the same transition One succeeds, the others receive 409

The First Version

Here is the handler written the way it naturally gets written when you add features one line at a time. It is correct enough to pass a quick manual test.

func (s *Server) transitionTask(w http.ResponseWriter, r *http.Request) {
    mediaType, _, err := mime.ParseMediaType(r.Header.Get("Content-Type"))
    if err != nil || mediaType != "application/json" {
        writeError(w, http.StatusUnsupportedMediaType, "UNSUPPORTED_MEDIA_TYPE", "Content-Type must be application/json")
        return
    }

    var req struct {
        To Status `json:"to"`
    }
    r.Body = http.MaxBytesReader(w, r.Body, 1<<20)
    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields()
    if err := dec.Decode(&req); err != nil {
        writeError(w, http.StatusBadRequest, "INVALID_ARGUMENT", "invalid request body")
        return
    }

    switch req.To {
    case StatusPending, StatusRunning, StatusCompleted, StatusFailed, StatusCancelled:
    default:
        writeError(w, http.StatusBadRequest, "INVALID_ARGUMENT", "to must be a valid status")
        return
    }

    s.store.mu.Lock()
    defer s.store.mu.Unlock()

    task, ok := s.store.tasks[r.PathValue("id")]
    if !ok {
        writeError(w, http.StatusNotFound, "NOT_FOUND", "task not found")
        return
    }

    allowed := false
    switch task.Status {
    case StatusPending:
        allowed = req.To == StatusRunning || req.To == StatusCancelled
    case StatusRunning:
        allowed = req.To == StatusCompleted || req.To == StatusFailed || req.To == StatusCancelled
    case StatusFailed:
        allowed = req.To == StatusPending
    }
    if !allowed {
        log.Printf("rejected transition %s -> %s for %s", task.Status, req.To, task.ID)
        writeError(w, http.StatusConflict, "INVALID_TRANSITION",
            fmt.Sprintf("cannot change status from %s to %s", task.Status, req.To))
        return
    }

    task.Status = req.To
    task.UpdatedAt = time.Now().UTC()
    s.store.tasks[task.ID] = task

    log.Printf("task %s moved to %s", task.ID, task.Status)
    writeJSON(w, http.StatusOK, task)
}

It runs, and it enforces the rules. Now read it as a reviewer would, asking what each part is responsible for.

Reading the Problem

This single function does five different jobs.

Job Lines it occupies What is wrong with it being here
Decoding and content negotiation The first block Copied from createTask; every new endpoint will copy it again
Validation The switch req.To block The list of valid statuses is now a second copy of knowledge that belongs to the task
Business rules The allowed switch Cannot be tested without constructing an HTTP request, and cannot be reused by a background worker
State change Direct access to s.store.tasks The handler reaches into the store’s private internals and bypasses its API
Response and logging The final lines Error shaping is repeated, with each branch building its own response

Three of these problems are worse than they look.

The lock is held while writing the response. defer s.store.mu.Unlock() releases the lock only when the function returns, which is after writeJSON has pushed bytes to the client. If that client is slow, every other request that needs the store waits behind it. A single slow connection can stall the service. Nothing in the code looks wrong, and in testing nothing would be, because test clients are fast.

The rules are trapped. The transition table from Chapter 3 now exists as a nested switch inside an HTTP handler. To test whether completed can go to pending, you must build a request, a recorder, and a server. When a background worker later needs to move tasks through the same lifecycle, it would have to duplicate the rules or call the HTTP endpoint.

It is easy to get wrong in the small. Every writeError here is followed by a return. Forget one, and the function continues to run, writing a second response on top of the first. Go reports this only as a log line about a superfluous WriteHeader call, and the client receives a corrupted response. A function with many exits has many chances for that mistake.

This is the pressure the abstraction answers. We do not refactor because the function is long. We refactor because it mixes responsibilities, and every mixed responsibility is a place where a change to one concern can break another.

The Shape of a Good Handler

Before changing anything, decide what a handler is for. Its job is to translate between HTTP and the application. It should do exactly four things, in order.

1. Decode     turn the HTTP request into plain values
2. Validate   check what can be checked from the input alone
3. Call       hand plain values to the application and receive a result or an error
4. Respond    turn the result or error into an HTTP response
A handler does A handler does not
Read the path, query, headers, and body Know the rules of the lifecycle
Check that input is well formed Reach into storage internals
Choose status codes and error codes Hold locks
Write the response Perform multi-step state changes

The right-hand column is the important one. It is a list of things the handler knows nothing about, and those ignorances are what make the code easy to change.

The Refactor

We work in three moves, and each one removes one of the problems above.

Move 1: Give the rules a home

The transition table becomes data in task.go, with a small function to query it. It is plain Go with no HTTP in sight.

var allowedTransitions = map[Status][]Status{
    StatusPending: {StatusRunning, StatusCancelled},
    StatusRunning: {StatusCompleted, StatusFailed, StatusCancelled},
    StatusFailed:  {StatusPending},
}

func (s Status) Valid() bool {
    switch s {
    case StatusPending, StatusRunning, StatusCompleted, StatusFailed, StatusCancelled:
        return true
    }
    return false
}

func CanTransition(from, to Status) bool {
    for _, next := range allowedTransitions[from] {
        if next == to {
            return true
        }
    }
    return false
}

type TransitionError struct {
    From Status
    To   Status
}

func (e *TransitionError) Error() string {
    return fmt.Sprintf("cannot change status from %s to %s", e.From, e.To)
}

Terminal states have no entry in the map, so ranging over them yields nothing and no transition is allowed, which matches the table in Chapter 3. TransitionError is a custom error type: a struct with an Error() string method satisfies the error interface. Carrying the two statuses lets callers inspect why a transition failed instead of parsing a message.

Move 2: Make the store own the state change

The check and the write must happen as one step. If they were separate, two callers could both pass the check and both write, which is exactly the collision Chapter 3 told us to prevent. Putting both inside the store’s lock makes the decision atomic, and the losing caller simply finds the task already moved.

func (s *Store) Transition(id string, to Status) (Task, error) {
    s.mu.Lock()
    defer s.mu.Unlock()

    task, ok := s.tasks[id]
    if !ok {
        return Task{}, ErrNotFound
    }
    if !CanTransition(task.Status, to) {
        return Task{}, &TransitionError{From: task.Status, To: to}
    }

    task.Status = to
    task.UpdatedAt = time.Now().UTC()
    s.tasks[id] = task
    return task, nil
}

The method returns the task by value and releases the lock on return. By the time the handler writes anything to the network, the lock is long gone, which fixes the slow-client problem without the handler knowing it ever existed. The collision policy, reject the loser, falls out of the structure for free: the second caller of “start this task” sees running and is rejected as an invalid transition.

Move 3: One place to translate errors

Both the 404 and the 409 are translations from the application’s vocabulary to HTTP. We centralize them.

func handleError(w http.ResponseWriter, err error) {
    var transitionErr *TransitionError

    switch {
    case errors.Is(err, ErrNotFound):
        writeError(w, http.StatusNotFound, "NOT_FOUND", "task not found")
    case errors.As(err, &transitionErr):
        writeError(w, http.StatusConflict, "INVALID_TRANSITION", transitionErr.Error())
    default:
        log.Printf("internal error: %v", err)
        writeError(w, http.StatusInternalServerError, "INTERNAL", "internal error")
    }
}

errors.Is matches a specific error value, and errors.As matches an error type and extracts it. The default branch is the safety net: anything unrecognized becomes a generic 500, with the detail logged and withheld from the client.

The result

With those pieces in place, the handler shrinks to its four jobs.

type transitionRequest struct {
    To Status `json:"to"`
}

func (s *Server) transitionTask(w http.ResponseWriter, r *http.Request) {
    var req transitionRequest
    if !decodeJSON(w, r, &req) {
        return
    }
    if !req.To.Valid() {
        writeError(w, http.StatusBadRequest, "INVALID_ARGUMENT", "to must be a valid status")
        return
    }

    task, err := s.store.Transition(r.PathValue("id"), req.To)
    if err != nil {
        handleError(w, err)
        return
    }

    writeJSON(w, http.StatusOK, task)
}

Eighteen lines, and each one maps to decode, validate, call, or respond. Register it in routes():

mux.HandleFunc("POST /tasks/{id}/transition", s.transitionTask)

The other handlers adopt the same shape. getTask loses its inline error branching:

func (s *Server) getTask(w http.ResponseWriter, r *http.Request) {
    task, err := s.store.Get(r.PathValue("id"))
    if err != nil {
        handleError(w, err)
        return
    }

    writeJSON(w, http.StatusOK, task)
}

In createTask, the failure branch after s.store.Create(title) becomes a call to handleError(w, err) in the same way. A new error type is now one added case in one function, and every handler benefits.

One more Go detail deserves a mention. mux.HandleFunc("POST /tasks", s.createTask) passes s.createTask as a value. This is a method value: a method bound to a particular receiver, here the Server, so the router can call it later as an ordinary function. It is how handlers get access to the store without global variables.

Testing What We Extracted

The payoff of the refactor is that each concern can now be tested at its own level. The lifecycle rules need no HTTP at all. This test restates the Chapter 3 table independently of the code, and checks every possible pair.

func TestCanTransition(t *testing.T) {
    allowed := map[[2]Status]bool{
        {StatusPending, StatusRunning}:   true,
        {StatusPending, StatusCancelled}: true,
        {StatusRunning, StatusCompleted}: true,
        {StatusRunning, StatusFailed}:    true,
        {StatusRunning, StatusCancelled}: true,
        {StatusFailed, StatusPending}:    true,
    }
    all := []Status{StatusPending, StatusRunning, StatusCompleted, StatusFailed, StatusCancelled}

    for _, from := range all {
        for _, to := range all {
            want := allowed[[2]Status{from, to}]
            if got := CanTransition(from, to); got != want {
                t.Errorf("CanTransition(%s, %s) = %v, want %v", from, to, got, want)
            }
        }
    }
}

Twenty-five combinations are covered by one loop, and any change to the lifecycle that is not also a change to the test fails loudly. That is what it looks like when a design document becomes executable.

The collision policy from Chapter 3 gets its own test, and this is the one that proves the atomicity claim.

func TestTransitionCollision(t *testing.T) {
    store := NewStore()
    task, err := store.Create("collide")
    if err != nil {
        t.Fatal(err)
    }

    const attempts = 20
    var wg sync.WaitGroup
    var mu sync.Mutex
    wins, conflicts := 0, 0

    for i := 0; i < attempts; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            _, err := store.Transition(task.ID, StatusRunning)

            mu.Lock()
            defer mu.Unlock()

            var transitionErr *TransitionError
            switch {
            case err == nil:
                wins++
            case errors.As(err, &transitionErr):
                conflicts++
            default:
                t.Errorf("unexpected error: %v", err)
            }
        }()
    }
    wg.Wait()

    if wins != 1 || conflicts != attempts-1 {
        t.Fatalf("wins = %d, conflicts = %d; want 1 and %d", wins, conflicts, attempts-1)
    }
}

Twenty goroutines race to start the same task. Exactly one wins, and nineteen are rejected. Run it with -race many times; it should never flake. Finally, a thin test of the handler itself, which now only needs to verify the HTTP translation.

func TestTransitionEndpoint(t *testing.T) {
    h := newTestHandler()
    const jsonType = "application/json"

    rec := send(h, http.MethodPost, "/tasks", jsonType, `{"title":"Write chapter one"}`)
    var created Task
    if err := json.NewDecoder(rec.Body).Decode(&created); err != nil {
        t.Fatalf("decode created task: %v", err)
    }
    path := "/tasks/" + created.ID + "/transition"

    tests := []struct {
        name       string
        path       string
        body       string
        wantStatus int
    }{
        {"start", path, `{"to":"running"}`, http.StatusOK},
        {"start again", path, `{"to":"running"}`, http.StatusConflict},
        {"unknown status", path, `{"to":"banana"}`, http.StatusBadRequest},
        {"unknown task", "/tasks/tsk_nope/transition", `{"to":"running"}`, http.StatusNotFound},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            rec := send(h, http.MethodPost, tt.path, jsonType, tt.body)
            if rec.Code != tt.wantStatus {
                t.Fatalf("status = %d, want %d", rec.Code, tt.wantStatus)
            }
        })
    }
}

The cases run in order against shared state: the first starts the task, and the second proves a repeat is rejected. The business rules are covered elsewhere, so the handler test stays small.

What the Refactor Cost

Every abstraction has a price, and honesty about it is part of the method.

What we gained What we sacrificed
Rules testable and reusable without HTTP The rules now live in two files, task.go and store.go, instead of one function
The lock is no longer held across network writes The store has grown a responsibility it arguably should not have
One place to translate errors A level of indirection when reading a handler
Handlers short enough to read at a glance A reader must now follow calls to see the whole behavior

The second row matters. The store is deciding whether a transition is legal, and that is a business decision, not a storage concern. We put it there because the check and the write must be atomic, and the store owns the lock. It is a pragmatic compromise, not a clean design. Chapter 17 introduces a service layer to hold decisions, and Chapter 13 shows how a database makes the check-and-write atomic without a process-wide lock. Both will move this code again. We keep it here for now because the problem is visible and the cost of moving it later is small.

What Is Still Wrong

Problem Where it is fixed
A client that retries a transition after a timeout receives a 409, though the first attempt succeeded Chapter 10
Handlers still call the store directly, with no layer for decisions Chapter 17
decodeJSON writes a response and returns a boolean, while handleError takes an error: two styles Chapter 8
No request IDs or request logging Chapter 7
Anyone can transition any task Chapter 9

The first row connects back to Chapter 5. The uncertainty about whether a request took effect now has a concrete symptom: an honest client doing the right thing is told its request conflicted with itself.

Engineering Lens

What problem did we solve? We moved the lifecycle rules, state changes, and error translation out of the handler so that each concern can be tested and changed on its own, and so that the handler returned to its single job.

What complexity did we introduce? A custom error type, a central error mapper, and more files. The code is easier to change and harder to read top to bottom in one sitting.

What failure modes appeared? A lock held across a network write, missing return statements after error responses, and rules duplicated between handlers and workers. The refactor removes the first and third and reduces the second.

What would break at 10× scale? The single process-wide lock. Every state change in the system queues behind one mutex, and a second instance of the service would not share it at all. Both limits point toward the database transactions of Part III.

When should we not refactor this way? When there is one endpoint, no second consumer of the rules, and no concurrency. A twenty-line handler that does one thing does not need an error mapper. We extracted because a second endpoint arrived and the duplication became visible, not before.

Exercises

  1. In the first-version handler, delete the return after the 404 response and send a request for a missing task. What does the client receive, and what appears in the server log?
  2. In the original handler, add a time.Sleep(5 * time.Second) just before writeJSON. Send two requests at once to different tasks. Why is the second one delayed, and does the refactored version have the same problem?
  3. Add the status blocked to the lifecycle. How many places in the code and tests must change? What does that number tell you about where the lifecycle knowledge lives?
  4. Add a GET /tasks/{id}/history endpoint design to a page of notes, without implementing it. Which of the four handler jobs does it need, and what would the application layer have to provide?
  5. A client sends the same {"to":"running"} request twice because the first response was lost. Write down what the client observes and what it should do. Is the 409 the right answer for the second request? What would an idempotent design return instead?

Chapter 7 gives Forge a proper router and middleware. Request IDs, recovery from panics, and structured request logging all arrive there, along with JSON error bodies for the router’s own 404 and 405 responses, closing the last gap in our error contract.

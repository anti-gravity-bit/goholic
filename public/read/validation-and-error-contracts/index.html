Chapter 8: Validation and Error Contracts

By Abir Sarkar · 15 min read · Published 2026-10-03 · LinkedIn

When a request goes wrong, the response is the only conversation the client will ever have with your system. A good error response lets a program decide what to do next and lets a person understand what happened. A bad one forces the client to guess, and clients that guess usually guess by parsing text.

The errors in Forge today are functional and consistent in shape. They are also quietly inadequate, and this chapter shows why and fixes it.

The Problem, Made Visible

Send a request that is wrong in an interesting way:

$ curl -s -X POST localhost:8080/tasks \
    -H 'Content-Type: application/json' \
    -d '{"titel":"Write chapter one"}'
{"error":{"code":"INVALID_ARGUMENT","message":"request body must be valid JSON with known fields"}}

The response says the request is wrong. It does not say which field, so a developer must read the message and work out that titel is the problem. A form in a web client cannot highlight the field that needs attention, because there is nothing machine-readable to attach the error to.

Now imagine the client author who wants to show a friendly message when the title is missing. The only thing available is the message string, so the code ends up as if (error.message.includes("title")). It works until someone improves the wording, at which point the client silently breaks. A message written for humans has become part of the contract, and no one chose that.

Three weaknesses are behind this.

Weakness Consequence
Errors do not identify which field is at fault Clients cannot attach errors to inputs
The message is the only structured signal Clients parse prose, and rewording becomes a breaking change
Errors are produced in two different styles Handlers that write errors and helpers that return them have to be kept consistent by hand

A Taxonomy of Failure

Before designing a response, classify what can go wrong. Every error a backend produces falls into one of five categories, and the category decides almost everything about how it should be handled.

Category Forge example Whose fault Typical status Client should retry? How we record it
Validation Title missing or too long The caller 400 No, fix the request Access log only
Domain Transition not allowed, task not found The request vs. current state 404, 409 Only after the state changes Access log only
Dependency The database times out, a payment API returns an error An external system 503 or 504 Yes, with backoff Warning with the cause
Infrastructure Out of file descriptors, connection pool exhausted Our own environment 500 or 503 Possibly Error, and an alert
Unexpected A nil pointer dereference, a panic Us, a bug 500 No, it will fail again Error with stack trace, and a page

Forge has so far produced only the first two kinds and the last. The in-memory store cannot time out or run out of connections. Part III introduces a real database, and with it the dependency and infrastructure categories. The model has to exist before they arrive, so that the first database timeout lands in a prepared place instead of falling into a generic 500.

The distinction between the two middle categories is subtle. A dependency failure is a system we call failing or being slow. An infrastructure failure is the platform we run on failing. Both are usually temporary, which makes them candidates for retries, and both are invisible to the client except as a status code.

Two principles follow from the table.

The client and the operator are different audiences. The client needs to know whether to fix the request, wait, or give up. The operator needs the full cause. A response that says connection refused to 10.0.0.5:5432 helps an attacker and confuses a client, while a log line that says only internal error helps nobody. Each audience gets its own version of the truth.

Only the unexpected deserve alarm. Validation and domain errors are the system working correctly. Logging each one as an error trains the on-call engineer to ignore the error log. Reserve loud signals for what no one planned for.

Designing the Contract

Here is the response shape we adopt for every error, from every endpoint and every layer.

{
  "error": {
    "code": "INVALID_ARGUMENT",
    "message": "request validation failed",
    "details": [
      {
        "field": "title",
        "code": "REQUIRED",
        "message": "title is required"
      }
    ],
    "request_id": "b41f6a0c9d3e7a52"
  }
}

Each field makes a different promise to the client.

Field Promise
code Stable and machine-readable. Clients may branch on it. Existing codes are never renamed or reused for a different meaning
message For humans. May be reworded at any time. Clients must never parse it
details Optional. Present for validation failures, one entry per problem, each with its own stable code
request_id Always present. The value to quote when asking for help, matching the X-Request-ID header and the server’s logs

The central design choice is the separation of code from message. Programs read the first, people read the second, and neither is allowed to depend on the other. This also settles an ongoing question: it is safe to add a new code, because clients treat unknown codes as a generic failure of the right category, but removing or renaming a code breaks them.

The HTTP status and the error code work together. The status gives the category, so generic infrastructure such as proxies and retry logic can act on it. The code gives the specific reason, so applications can act on it.

Code Status Meaning
INVALID_ARGUMENT 400 The request is malformed or fails validation, with details
UNSUPPORTED_MEDIA_TYPE 415 The body is not JSON
PAYLOAD_TOO_LARGE 413 The body exceeds the size limit
NOT_FOUND 404 The task or route does not exist
METHOD_NOT_ALLOWED 405 The path exists but not for this method
INVALID_TRANSITION 409 The status change is not allowed from the current state
INTERNAL 500 An unexpected failure, with no detail exposed

An Error Type That Knows Its Own Response

The design needs a Go type that carries everything a response needs. We create errors.go:

package main

import (
    "errors"
    "log/slog"
    "net/http"
)

type FieldError struct {
    Field   string `json:"field"`
    Code    string `json:"code"`
    Message string `json:"message"`
}

type APIError struct {
    Status    int          `json:"-"`
    Code      string       `json:"code"`
    Message   string       `json:"message"`
    Details   []FieldError `json:"details,omitempty"`
    RequestID string       `json:"request_id,omitempty"`

    cause error
}

func (e *APIError) Error() string { return e.Code + ": " + e.Message }
func (e *APIError) Unwrap() error { return e.cause }

func invalidArgument(message string, details ...FieldError) *APIError {
    return &APIError{Status: http.StatusBadRequest, Code: "INVALID_ARGUMENT", Message: message, Details: details}
}

func notFound(message string) *APIError {
    return &APIError{Status: http.StatusNotFound, Code: "NOT_FOUND", Message: message}
}

func conflict(code, message string) *APIError {
    return &APIError{Status: http.StatusConflict, Code: code, Message: message}
}

func internalError(cause error) *APIError {
    return &APIError{Status: http.StatusInternalServerError, Code: "INTERNAL", Message: "internal error", cause: cause}
}

Three details deserve attention. The Status field is tagged json:"-" so it controls the HTTP status line but never appears in the body. The cause field is unexported, so it can carry the real underlying error to the logs without any possibility of being serialized to the client. And Unwrap lets errors.Is and errors.As see through an APIError to the cause beneath it, which keeps the whole chain inspectable.

One Place Where Errors Become Responses

The two styles have to become one. We make a single rule: handlers return errors, and exactly one function turns an error into a response. Handlers no longer write error responses at all.

First, the translation point. Domain errors from the store become API errors here, at the boundary, exactly as Chapter 2 prescribed.

func toAPIError(err error) *APIError {
    var apiErr *APIError
    var transitionErr *TransitionError

    switch {
    case errors.As(err, &apiErr):
        return apiErr
    case errors.Is(err, ErrNotFound):
        return notFound("task not found")
    case errors.As(err, &transitionErr):
        return conflict("INVALID_TRANSITION", transitionErr.Error())
    default:
        return internalError(err)
    }
}

The default branch is the safety net. Anything not recognized becomes an INTERNAL error with the original attached as its private cause, so a bug can never leak its own text to a client. Then the function that writes the response:

type errorBody struct {
    Error *APIError `json:"error"`
}

func writeAPIError(w http.ResponseWriter, r *http.Request, logger *slog.Logger, err error) {
    out := *toAPIError(err)
    out.RequestID = requestIDFromContext(r.Context())

    if out.cause != nil {
        logger.ErrorContext(r.Context(), "request failed",
            slog.String("request_id", out.RequestID),
            slog.String("code", out.Code),
            slog.Any("error", out.cause),
        )
    }

    writeJSON(w, out.Status, errorBody{Error: &out})
}

It copies the error before attaching the request ID, so a shared error value is never mutated by concurrent requests. It logs only when there is a private cause, which matches the taxonomy: validation and domain errors have no cause and need no log line, while unexpected ones always do.

Finally, an adapter lets handlers return an error. A handler that returns error cannot forget to stop, because stopping and failing are the same statement.

type handlerFunc func(w http.ResponseWriter, r *http.Request) error

func (s *Server) handle(h handlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        if err := h(w, r); err != nil {
            writeAPIError(w, r, s.logger, err)
        }
    }
}

This also removes a whole class of bug. In Chapter 6 we noted that forgetting a return after writing an error corrupts the response. Now the pattern is return invalidArgument(...), and there is no separate write step to forget.

Validation That Reports Everything

Validation should report every problem it can find, not just the first. A client that has to fix errors one at a time, resubmitting after each, is a client that has been badly served. We change validateTitle in task.go to describe a problem as a FieldError, and the file no longer needs its errors import.

func validateTitle(title string) *FieldError {
    if title == "" {
        return &FieldError{Field: "title", Code: "REQUIRED", Message: "title is required"}
    }
    if utf8.RuneCountInString(title) > maxTitleLength {
        return &FieldError{
            Field:   "title",
            Code:    "TOO_LONG",
            Message: fmt.Sprintf("title must be at most %d characters", maxTitleLength),
        }
    }
    return nil
}

The field-level code values are as stable as the top-level ones. REQUIRED and TOO_LONG are things a client can map to its own wording, in its own language, which the server’s message could never do.

Decoding problems get the same treatment. Instead of one catch-all message, each failure mode is classified, and where the JSON library tells us which field is involved, we pass that on.

func decodeError(err error) *APIError {
    var (
        maxBytesErr *http.MaxBytesError
        syntaxErr   *json.SyntaxError
        typeErr     *json.UnmarshalTypeError
    )

    switch {
    case errors.As(err, &maxBytesErr):
        return &APIError{
            Status:  http.StatusRequestEntityTooLarge,
            Code:    "PAYLOAD_TOO_LARGE",
            Message: fmt.Sprintf("request body must be at most %d bytes", maxBodyBytes),
        }
    case errors.Is(err, io.EOF):
        return invalidArgument("request body is required")
    case errors.As(err, &syntaxErr), errors.Is(err, io.ErrUnexpectedEOF):
        return invalidArgument("request body is not valid JSON")
    case errors.As(err, &typeErr):
        return invalidArgument("request body has a field of the wrong type", FieldError{
            Field:   typeErr.Field,
            Code:    "INVALID_TYPE",
            Message: fmt.Sprintf("%s must be of type %s", typeErr.Field, typeErr.Type),
        })
    }

    if rest, ok := strings.CutPrefix(err.Error(), "json: unknown field "); ok {
        if name, uerr := strconv.Unquote(rest); uerr == nil {
            return invalidArgument("request body contains an unknown field", FieldError{
                Field:   name,
                Code:    "UNKNOWN_FIELD",
                Message: fmt.Sprintf("%s is not a known field", name),
            })
        }
    }

    return invalidArgument("request body is not valid JSON")
}

The unknown-field branch deserves a candid comment. Go’s JSON decoder reports an unknown field only as an error message, with no dedicated type, so extracting the name means parsing text. That is exactly the fragility we warned clients against, and here it is our own code doing it. The honest response is to contain the risk: the parse is confined to one function, it falls through to a safe generic answer if the format ever changes, and a test pins the behavior so a new Go release that rewords the message fails our build instead of quietly degrading our responses. Depending on something fragile is sometimes unavoidable. Depending on it invisibly is the real mistake.

The decoding helper now returns an error instead of writing a response and returning a boolean:

func decodeJSON(w http.ResponseWriter, r *http.Request, dst any) error {
    mediaType, _, err := mime.ParseMediaType(r.Header.Get("Content-Type"))
    if err != nil || mediaType != "application/json" {
        return &APIError{
            Status:  http.StatusUnsupportedMediaType,
            Code:    "UNSUPPORTED_MEDIA_TYPE",
            Message: "Content-Type must be application/json",
        }
    }

    r.Body = http.MaxBytesReader(w, r.Body, maxBodyBytes)
    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields()

    if err := dec.Decode(dst); err != nil {
        return decodeError(err)
    }
    if err := dec.Decode(&struct{}{}); !errors.Is(err, io.EOF) {
        return invalidArgument("request body must contain a single JSON value")
    }
    return nil
}

Note the final return nil, and that no path returns a possibly-nil *APIError through the error return. That is deliberate, and it avoids one of Go’s best-known traps: a nil *APIError stored in an error variable is not equal to nil, because the interface still holds a type. A function returning error must return the literal nil for success.

The Handlers, Simplified Again

With all of that in place, each handler reduces to its four jobs, and the failure path is one statement.

func (s *Server) createTask(w http.ResponseWriter, r *http.Request) error {
    var req createTaskRequest
    if err := decodeJSON(w, r, &req); err != nil {
        return err
    }

    title := strings.TrimSpace(req.Title)
    if problem := validateTitle(title); problem != nil {
        return invalidArgument("request validation failed", *problem)
    }

    task, err := s.store.Create(title)
    if err != nil {
        return err
    }

    w.Header().Set("Location", "/tasks/"+task.ID)
    writeJSON(w, http.StatusCreated, task)
    return nil
}

func (s *Server) getTask(w http.ResponseWriter, r *http.Request) error {
    task, err := s.store.Get(r.PathValue("id"))
    if err != nil {
        return err
    }

    writeJSON(w, http.StatusOK, task)
    return nil
}

func (s *Server) transitionTask(w http.ResponseWriter, r *http.Request) error {
    var req transitionRequest
    if err := decodeJSON(w, r, &req); err != nil {
        return err
    }
    if !req.To.Valid() {
        return invalidArgument("request validation failed", FieldError{
            Field:   "to",
            Code:    "INVALID_VALUE",
            Message: "to must be a valid status",
        })
    }

    task, err := s.store.Transition(r.PathValue("id"), req.To)
    if err != nil {
        return err
    }

    writeJSON(w, http.StatusOK, task)
    return nil
}

listTasks and health change in the same mechanical way: they gain an error return and end with return nil. The routes are registered through the adapter:

mux.HandleFunc("GET /health", s.handle(s.health))
mux.HandleFunc("POST /tasks", s.handle(s.createTask))
mux.HandleFunc("GET /tasks", s.handle(s.listTasks))
mux.HandleFunc("GET /tasks/{id}", s.handle(s.getTask))
mux.HandleFunc("POST /tasks/{id}/transition", s.handle(s.transitionTask))

The old writeError function, the errorDetail type, and handleError are all deleted. The two remaining places that wrote errors by hand, the recovery middleware and the router wrapper, move to the shared path. Recovery already logs the panic and its stack, so it passes an error with no private cause, which avoids a duplicate log line:

writeAPIError(w, r, logger, internalError(nil))

And the router wrapper builds its two errors as API errors, which also gives them request IDs:

case http.StatusMethodNotAllowed:
    if allow := probe.header.Get("Allow"); allow != "" {
        w.Header().Set("Allow", allow)
    }
    writeAPIError(w, r, logger, &APIError{
        Status:  http.StatusMethodNotAllowed,
        Code:    "METHOD_NOT_ALLOWED",
        Message: "method not allowed for this path",
    })
case http.StatusNotFound:
    writeAPIError(w, r, logger, notFound("route not found"))

routerErrors now takes the logger as a second parameter, and routes() passes s.logger to it.

Testing the Contract

The test suite should state the contract directly. The first table checks the shape of validation errors, including which field each one points to.

type testErrorBody struct {
    Error APIError `json:"error"`
}

func TestValidationErrorsNameTheirField(t *testing.T) {
    h := newTestHandler()
    const jsonType = "application/json"

    tests := []struct {
        name      string
        body      string
        wantField string
        wantCode  string
    }{
        {"missing title", `{}`, "title", "REQUIRED"},
        {"title too long", `{"title":"` + strings.Repeat("a", 201) + `"}`, "title", "TOO_LONG"},
        {"wrong type", `{"title":123}`, "title", "INVALID_TYPE"},
        {"unknown field", `{"title":"x","colour":"red"}`, "colour", "UNKNOWN_FIELD"},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            rec := send(h, http.MethodPost, "/tasks", jsonType, tt.body)
            if rec.Code != http.StatusBadRequest {
                t.Fatalf("status = %d, want %d", rec.Code, http.StatusBadRequest)
            }

            var body testErrorBody
            if err := json.NewDecoder(rec.Body).Decode(&body); err != nil {
                t.Fatalf("decode: %v", err)
            }
            if body.Error.Code != "INVALID_ARGUMENT" {
                t.Fatalf("code = %q, want INVALID_ARGUMENT", body.Error.Code)
            }
            if len(body.Error.Details) != 1 {
                t.Fatalf("details = %d entries, want 1", len(body.Error.Details))
            }
            got := body.Error.Details[0]
            if got.Field != tt.wantField || got.Code != tt.wantCode {
                t.Fatalf("detail = {%s %s}, want {%s %s}", got.Field, got.Code, tt.wantField, tt.wantCode)
            }
        })
    }
}

The unknown field row is the test that pins our dependence on the library’s message, as promised above. The next test enforces the two-audience principle directly: an unexpected error carrying sensitive text must never reach the client, and the response must still carry the request ID.

func TestInternalErrorsDoNotLeakDetails(t *testing.T) {
    logger := slog.New(slog.NewTextHandler(io.Discard, nil))
    srv := NewServer(NewStore(), logger)

    failing := srv.handle(func(w http.ResponseWriter, r *http.Request) error {
        return errors.New("dial tcp 10.0.0.5:5432: connection refused")
    })
    h := chain(failing, requestID)

    rec := httptest.NewRecorder()
    h.ServeHTTP(rec, httptest.NewRequest(http.MethodGet, "/", nil))

    if rec.Code != http.StatusInternalServerError {
        t.Fatalf("status = %d, want %d", rec.Code, http.StatusInternalServerError)
    }
    if strings.Contains(rec.Body.String(), "10.0.0.5") {
        t.Fatal("internal error details leaked to the client")
    }

    var body testErrorBody
    if err := json.NewDecoder(rec.Body).Decode(&body); err != nil {
        t.Fatalf("decode: %v", err)
    }
    if body.Error.Code != "INTERNAL" {
        t.Fatalf("code = %q, want INTERNAL", body.Error.Code)
    }
    if body.Error.RequestID == "" || body.Error.RequestID != rec.Header().Get("X-Request-ID") {
        t.Fatalf("request_id = %q, header = %q", body.Error.RequestID, rec.Header().Get("X-Request-ID"))
    }
}

Notice that strings.Contains is run before the body is decoded. Reading rec.Body.String() does not consume the buffer, so the decode afterward still works.

What the Refactor Cost

What we gained What we sacrificed
Clients can attach errors to fields and branch on stable codes A larger response, and a contract we are now committed to keeping
One path from error to response, with no forgotten return Handlers no longer control their own error output, which can surprise newcomers
Private causes reach the logs and never the client Two parallel descriptions of every failure, one public and one private
Domain errors translated in exactly one place A growing switch that every new error type must be added to

The last row is a real cost and a real benefit at once. The switch in toAPIError is the single place that knows how every domain error appears to the outside world, which makes the contract auditable. It also means every new kind of failure must be registered there, and an error that is not registered becomes a 500, which is the safe default.

What Is Still Wrong

Problem Where it is fixed
No authentication or authorization, so 401 and 403 do not exist yet Chapter 9
Dependency and infrastructure errors are modeled but not yet produced Part III
Clients retrying 503 have no Retry-After guidance Chapter 31
The error code catalog exists only in this chapter Chapter 10

Engineering Lens

What problem did we solve? We gave every failure a category, a stable machine-readable code, field-level detail where it applies, and a request ID, and we routed all of it through one place so it cannot drift.

What complexity did we introduce? A custom error type, a translation function that grows with the domain, and the discipline of treating the error catalog as a public contract.

What failure modes appeared? Clients parsing messages, internal text leaking to callers, fragile parsing of library error text, the typed-nil trap, and error logs so noisy that real problems are ignored.

What would break at 10× scale? The log volume from unexpected errors during an incident. When a dependency fails, thousands of requests produce thousands of identical request failed lines at once, which is the moment rate limiting and log sampling earn their keep.

When should we not build this much? For an internal tool with a single known client, plain status codes and messages are enough. A formal error contract pays for itself when clients are independent, numerous, or built by people you will never meet.

Exercises

  1. Add an ErrUnavailable error to the store, as if a dependency had failed. Map it in toAPIError to a 503 with code UNAVAILABLE and a Retry-After: 1 header. Where does the header get set, given that APIError currently carries no headers?
  2. Add an optional description field, at most 1000 characters, to task creation. Change validation to return all problems at once, then send a body that violates both the title and description rules and confirm both appear in details.
  3. Choose a public API you use and read its error documentation. Classify each error it can return using the five categories in this chapter. Which category is least well handled?
  4. A future Go release rewords the unknown-field message. Which test fails, and what does the response to a client degrade into in the meantime? Is that acceptable?
  5. Write a small function that returns (*APIError)(nil) as an error, then print whether the result equals nil. Explain what you observe in terms of how an interface value is stored.

Chapter 9 puts a lock on the front door. We add users, passwords, and tokens, introduce the 401 and 403 categories, and use the middleware and error contract we have just built to make authentication a layer rather than a rewrite.

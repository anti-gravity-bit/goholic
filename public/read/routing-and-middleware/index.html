Chapter 7: Routing and Middleware

By Abir Sarkar · 15 min read · Published 2026-10-03 · LinkedIn

Forge now has four endpoints, and each one is a clean handler that decodes, validates, calls, and responds. They share a flaw that has nothing to do with any of them. Nobody is watching the front door.

If a handler panics, what does the client see? If two requests fail at the same moment, which log line belongs to which? When a customer reports “my request failed at 9:14,” how do you find it? These questions concern every endpoint equally, and the answers belong in one place rather than being repeated in every handler. That place is middleware.

The Problem, Made Visible

Add a deliberately broken endpoint to routes() for a moment:

mux.HandleFunc("GET /boom", func(w http.ResponseWriter, r *http.Request) {
    var tasks map[string]Task
    tasks["x"] = Task{} // writing to a nil map panics
})

Request it:

$ curl -i localhost:8080/boom
curl: (52) Empty reply from server

Go’s HTTP server recovers from handler panics so one bad request does not crash the process, but its recovery is blunt. It logs a stack trace to standard error in plain text and closes the connection. The client receives no status code, no JSON, and no explanation, only a dropped connection that looks exactly like a network failure. Our error contract from Chapter 3 promised that every failure produces a clear, consistent response. A panic quietly breaks that promise.

Three more gaps are in the same category.

Gap Symptom
No request identity Log lines from concurrent requests interleave with nothing connecting them
No access log Nothing records which requests arrived, how they ended, or how long they took
Router errors are plain text A 404 or 405 from the router ignores our error format entirely

Remove the /boom route before continuing. We will bring it back as a test.

Routing in Depth

Before wrapping the router, understand what it does. Go’s ServeMux matches a request to a handler using patterns, and since Go 1.22 a pattern can include a method and wildcards.

Pattern Matches
GET /tasks Exactly GET /tasks (and HEAD /tasks)
GET /tasks/{id} One path segment after /tasks/, captured as id
POST /tasks/{id}/transition A nested path with a captured segment in the middle
/static/ Everything beginning with /static/ (a subtree)
/files/{path...} The remainder of the path, however many segments
/{$} Exactly the root path and nothing else

When two patterns could match the same request, the more specific one wins, so GET /tasks/{id} takes precedence over a broad /tasks/. When two patterns conflict in a way the router cannot resolve, registration panics at startup. This is a gift. A routing ambiguity is discovered the first time you run the program, not after a deploy, which is the book’s philosophy implemented by the standard library.

Forge’s route tree grows as the chapters advance. Today it is small:

/
├── /health           GET
└── /tasks
    ├── GET, POST
    └── /{id}
        ├── GET
        └── /transition   POST

Chapter 9 adds /auth and /users branches. We add the first new route now, a health check that load balancers and orchestrators use to ask whether the process is alive:

func (s *Server) health(w http.ResponseWriter, r *http.Request) {
    writeJSON(w, http.StatusOK, map[string]string{"status": "ok"})
}

It deliberately touches nothing else. A liveness check that queries the database would report the process as dead whenever the database is slow, which is the wrong signal. Chapter 30 separates liveness from readiness properly.

What Middleware Is

A middleware is a function that takes a handler and returns a new handler that wraps it. In Go’s standard library, that is a function from http.Handler to http.Handler.

type middleware func(http.Handler) http.Handler

Here is the smallest useful one, which measures how long a request takes:

func timing(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)
        log.Printf("%s %s took %s", r.Method, r.URL.Path, time.Since(start))
    })
}

Everything before next.ServeHTTP runs on the way in, and everything after runs on the way out. Stacked together, middlewares form an onion: each layer sees the request on its way to the handler and the response on its way back.

Request
   ↓
┌─ Layer A ─────────────────────┐
│  ┌─ Layer B ───────────────┐  │
│  │  ┌─ Handler ─────────┐  │  │
│  │  │                   │  │  │
│  │  └───────────────────┘  │  │
│  └─────────────────────────┘  │
└───────────────────────────────┘
   ↓
Response

To apply several middlewares without nesting calls by hand, we write a small helper. The first one listed is the outermost layer.

func chain(h http.Handler, mws ...middleware) http.Handler {
    for i := len(mws) - 1; i >= 0; i-- {
        h = mws[i](h)
    }
    return h
}

It loops backwards so that chain(h, a, b, c) produces a(b(c(h))). Composition is the whole idea: each middleware does one thing, knows nothing about the others, and the order is decided in one visible line.

Middleware 1: Request ID

A request ID is a short unique label attached to every request, echoed in the response, and included in every log line the request produces. It is the thread that ties scattered evidence together.

type requestIDCtxKey struct{}

func requestID(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        id := r.Header.Get("X-Request-ID")
        if !validRequestID(id) {
            id = newRequestID()
        }

        w.Header().Set("X-Request-ID", id)
        ctx := context.WithValue(r.Context(), requestIDCtxKey{}, id)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

func requestIDFromContext(ctx context.Context) string {
    id, _ := ctx.Value(requestIDCtxKey{}).(string)
    return id
}

func newRequestID() string {
    b := make([]byte, 8)
    if _, err := rand.Read(b); err != nil {
        return "unknown"
    }
    return hex.EncodeToString(b)
}

func validRequestID(id string) bool {
    if id == "" || len(id) > 64 {
        return false
    }
    for _, c := range id {
        switch {
        case c >= 'a' && c <= 'z', c >= 'A' && c <= 'Z', c >= '0' && c <= '9', c == '-', c == '_':
        default:
            return false
        }
    }
    return true
}

Two decisions here are worth explaining.

We accept a client-supplied ID, but only a well-behaved one. Accepting an inbound ID lets a request keep one identity as it crosses several services, which is valuable later. But a header is attacker-controlled input that we are about to write into our logs. An unbounded or oddly shaped value could bloat the logs or confuse tools that parse them. So we accept short IDs made of safe characters and replace anything else.

The ID travels in the request’s context. A context.Context is Go’s standard way to carry request-scoped values, and later cancellation and deadlines, down through function calls. WithValue returns a new context holding our ID, and r.WithContext produces a copy of the request that carries it. The key is an unexported empty struct type, so no other package can accidentally collide with it. Chapter 24 treats context in depth, and the rule for now is to put only request-scoped facts in it, never dependencies.

Middleware 2: Access Logging

For each request we want one line that says what happened. Go gives us log/slog for structured logging, and Chapter 29 explores it fully. We need only the basics. To record the status code and the size of the response, we must observe what the handler writes, so we wrap the ResponseWriter.

type responseRecorder struct {
    http.ResponseWriter
    status      int
    bytes       int
    wroteHeader bool
}

func (rr *responseRecorder) WriteHeader(status int) {
    if !rr.wroteHeader {
        rr.status = status
        rr.wroteHeader = true
    }
    rr.ResponseWriter.WriteHeader(status)
}

func (rr *responseRecorder) Write(b []byte) (int, error) {
    if !rr.wroteHeader {
        rr.WriteHeader(http.StatusOK)
    }
    n, err := rr.ResponseWriter.Write(b)
    rr.bytes += n
    return n, err
}

func (rr *responseRecorder) Unwrap() http.ResponseWriter {
    return rr.ResponseWriter
}

The wrapper embeds the original ResponseWriter, so everything it does not override passes straight through. It records only the first status, mirroring what the server actually sends. The Unwrap method matters more than it looks. A bare wrapper silently hides optional capabilities of the underlying writer, such as flushing, and Go’s http.ResponseController uses Unwrap to find them again.

With the recorder in place, the logger is short:

func requestLogger(logger *slog.Logger) middleware {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            start := time.Now()
            rr := &responseRecorder{ResponseWriter: w, status: http.StatusOK}

            next.ServeHTTP(rr, r)

            level := slog.LevelInfo
            if rr.status >= http.StatusInternalServerError {
                level = slog.LevelError
            }
            logger.LogAttrs(r.Context(), level, "request",
                slog.String("request_id", requestIDFromContext(r.Context())),
                slog.String("method", r.Method),
                slog.String("path", r.URL.Path),
                slog.Int("status", rr.status),
                slog.Int("bytes", rr.bytes),
                slog.Float64("duration_ms", float64(time.Since(start).Microseconds())/1000),
            )
        })
    }
}

One line per request, as JSON, looks like this:

{"time":"2026-10-03T09:30:12.311Z","level":"INFO","msg":"request","request_id":"b41f6a0c9d3e7a52","method":"POST","path":"/tasks","status":201,"bytes":187,"duration_ms":0.42}

Note what we chose not to log. We record the path but not the query string, which can carry tokens. We log no headers and no bodies, which can carry passwords and personal data. A log is a permanent record that many people can read, so what goes into it deserves the same care as what goes into a response.

Middleware 3: Recovery

Recovery turns a panic into an ordinary error response.

func recoverer(logger *slog.Logger) middleware {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            defer func() {
                rec := recover()
                if rec == nil {
                    return
                }
                if rec == http.ErrAbortHandler {
                    panic(rec)
                }

                logger.ErrorContext(r.Context(), "panic recovered",
                    slog.String("request_id", requestIDFromContext(r.Context())),
                    slog.Any("panic", rec),
                    slog.String("stack", string(debug.Stack())),
                )
                writeError(w, http.StatusInternalServerError, "INTERNAL", "internal error")
            }()

            next.ServeHTTP(w, r)
        })
    }
}

recover stops a panic and returns its value, but it only works inside a deferred function, which is why defer and recovery are partners. The special case for http.ErrAbortHandler re-panics deliberately: that value is how a handler asks the server to abort a response without logging, and swallowing it would break that contract.

Recovery has a limit worth knowing. If the handler already sent the status line before it panicked, the client has been told 200 and we can no longer change our mind. Recovery cannot undo bytes already sent, and in that case the write attempt only produces a warning. This is another reason handlers should prepare their results fully before they begin writing.

The Order Matters

We now have three middlewares and must choose how to stack them. The Chapter 3 diagram of a request suggests a natural order: recovery on the outside, because it should catch everything, then request ID, then logging.

chain(handler, recoverer(logger), requestID, requestLogger(logger))

This reads sensibly, and it has a flaw that only shows up when something goes wrong. The test below sends a panicking request through the stack and demands that the access log contain a line for it, carrying the correct status and request ID.

func TestPanicIsRecoveredAndLogged(t *testing.T) {
    var buf bytes.Buffer
    logger := slog.New(slog.NewJSONHandler(&buf, nil))

    panicking := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        panic("boom")
    })
    h := chain(panicking, requestID, requestLogger(logger), recoverer(logger))

    rec := httptest.NewRecorder()
    h.ServeHTTP(rec, httptest.NewRequest(http.MethodGet, "/", nil))

    if rec.Code != http.StatusInternalServerError {
        t.Fatalf("status = %d, want %d", rec.Code, http.StatusInternalServerError)
    }
    id := rec.Header().Get("X-Request-ID")
    if id == "" {
        t.Fatal("response has no X-Request-ID")
    }

    found := false
    dec := json.NewDecoder(&buf)
    for dec.More() {
        var entry map[string]any
        if err := dec.Decode(&entry); err != nil {
            t.Fatalf("decode log line: %v", err)
        }
        if entry["msg"] != "request" {
            continue
        }
        found = true
        if entry["status"] != float64(http.StatusInternalServerError) {
            t.Errorf("logged status = %v, want %d", entry["status"], http.StatusInternalServerError)
        }
        if entry["request_id"] != id {
            t.Errorf("logged request_id = %v, want %s", entry["request_id"], id)
        }
    }
    if !found {
        t.Fatal("no access log line was written for the panicking request")
    }
}

The test uses the order requestID, requestLogger, recoverer. Run it with the first-instinct order instead and it fails at the last check. The reason is the onion. With recovery outermost, the panic travels through the logging layer on its way out, unwinding past the code that would have written the access log line. Recovery catches it afterward and writes a 500, but the request that most needs a log line is the one that never gets one.

With recovery inside logging, the panic is caught before it reaches the logger. Recovery writes the 500 through the logger’s own wrapped writer, control returns normally, and the logger sees a finished request with status 500 and logs it. The ordering rule that emerges is general: a layer sees an error only if the layers inside it do not absorb it, and a layer can observe only what happens inside it. Anything that needs to observe the final outcome of a request must sit outside whatever produces that outcome.

Position Middleware Why it sits here
Outermost Request ID Everything inside, including logs and recovery, can use the ID
Next Access logging Wraps recovery so it records the final status, even for panics
Next Recovery Closest to the handler so panics are absorbed before they escape
Later chapters Authentication Inside recovery, so a failure in auth code is also caught, and after the ID so rejected requests are traceable

The Router’s Own Errors

The last gap is the router’s plain-text 404 and 405. The router writes those itself, inside ServeMux, before any of our handlers run. To bring them into our format we put a small handler in front of the mux. It asks the mux what it would do, and takes over only when no route matches.

type statusProbe struct {
    header http.Header
    status int
}

func (p *statusProbe) Header() http.Header         { return p.header }
func (p *statusProbe) Write(b []byte) (int, error) { return len(b), nil }
func (p *statusProbe) WriteHeader(status int)      { p.status = status }

func routerErrors(mux *http.ServeMux) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        handler, pattern := mux.Handler(r)
        if pattern != "" {
            mux.ServeHTTP(w, r)
            return
        }

        probe := &statusProbe{header: make(http.Header)}
        handler.ServeHTTP(probe, r)

        switch probe.status {
        case http.StatusMethodNotAllowed:
            if allow := probe.header.Get("Allow"); allow != "" {
                w.Header().Set("Allow", allow)
            }
            writeError(w, http.StatusMethodNotAllowed, "METHOD_NOT_ALLOWED", "method not allowed for this path")
        case http.StatusNotFound:
            writeError(w, http.StatusNotFound, "NOT_FOUND", "route not found")
        default:
            handler.ServeHTTP(w, r)
        }
    })
}

ServeMux.Handler reports the handler that would serve a request and the pattern it matched. When no pattern matches, the pattern is empty and the handler is the mux’s built-in 404 or 405 responder. We run that responder against a throwaway statusProbe that only records the status and headers, then write our own JSON response in its place. The default branch handles anything else the mux might do, such as redirecting a non-canonical path, by letting it run for real.

There is one trap here. When a pattern does match, we must call mux.ServeHTTP and not the handler that Handler returned. Only ServeHTTP records the matched wildcards on the request, and calling the handler directly would make r.PathValue("id") return an empty string. The failure would be silent, which is exactly the kind a test should guard against, and the existing TestGetTask does.

Wiring It Together

The server now carries a logger, so it gets a constructor. This is dependency injection in its plainest Go form: whatever a type needs is passed in when it is built.

type Server struct {
    store  *Store
    logger *slog.Logger
}

func NewServer(store *Store, logger *slog.Logger) *Server {
    return &Server{store: store, logger: logger}
}

The new routes.go replaces the routes() method in handlers.go:

func (s *Server) routes() http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /health", s.health)
    mux.HandleFunc("POST /tasks", s.createTask)
    mux.HandleFunc("GET /tasks", s.listTasks)
    mux.HandleFunc("GET /tasks/{id}", s.getTask)
    mux.HandleFunc("POST /tasks/{id}/transition", s.transitionTask)

    return chain(routerErrors(mux), requestID, requestLogger(s.logger), recoverer(s.logger))
}

And main builds the logger once:

func main() {
    logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
    slog.SetDefault(logger)

    srv := NewServer(NewStore(), logger)

    httpServer := &http.Server{
        Addr:              ":8080",
        Handler:           srv.routes(),
        ReadHeaderTimeout: 5 * time.Second,
        ReadTimeout:       10 * time.Second,
        WriteTimeout:      10 * time.Second,
        IdleTimeout:       60 * time.Second,
    }

    logger.Info("forge listening", slog.String("addr", httpServer.Addr))
    if err := httpServer.ListenAndServe(); err != nil {
        logger.Error("server stopped", slog.Any("error", err))
        os.Exit(1)
    }
}

The call to slog.SetDefault has a useful side effect. Since Go 1.21, the older log.Printf calls scattered through our handlers are routed through the default slog logger, so they come out as JSON too. We get one consistent log stream without touching those lines, and Chapter 29 will convert them properly.

Middleware that applies to every route is wired here, around the whole mux. Middleware for only some routes wraps those handlers individually, which is how Chapter 9 will protect /tasks while leaving /health open:

mux.Handle("POST /tasks", requireAuth(http.HandlerFunc(s.createTask)))

Testing the Middleware

The test helper now builds the server through its constructor and discards log output:

func newTestHandler() http.Handler {
    logger := slog.New(slog.NewTextHandler(io.Discard, nil))
    return NewServer(NewStore(), logger).routes()
}

Beyond the panic test above, two more cases pin down the other behaviors.

func TestRequestID(t *testing.T) {
    ok := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK)
    })
    h := chain(ok, requestID)

    tests := []struct {
        name     string
        inbound  string
        wantEcho bool
    }{
        {"valid id is echoed", "abc-123_X", true},
        {"missing id is generated", "", false},
        {"unsafe characters are replaced", "bad id!", false},
        {"overlong id is replaced", strings.Repeat("a", 65), false},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            req := httptest.NewRequest(http.MethodGet, "/", nil)
            if tt.inbound != "" {
                req.Header.Set("X-Request-ID", tt.inbound)
            }
            rec := httptest.NewRecorder()
            h.ServeHTTP(rec, req)

            got := rec.Header().Get("X-Request-ID")
            if got == "" {
                t.Fatal("response has no X-Request-ID")
            }
            if tt.wantEcho && got != tt.inbound {
                t.Fatalf("id = %q, want %q", got, tt.inbound)
            }
            if !tt.wantEcho && got == tt.inbound {
                t.Fatalf("id %q should have been replaced", tt.inbound)
            }
        })
    }
}

func TestRouterErrorsAreJSON(t *testing.T) {
    h := newTestHandler()

    tests := []struct {
        name       string
        method     string
        path       string
        wantStatus int
        wantCode   string
    }{
        {"unknown route", http.MethodGet, "/nope", http.StatusNotFound, "NOT_FOUND"},
        {"wrong method", http.MethodPut, "/tasks", http.StatusMethodNotAllowed, "METHOD_NOT_ALLOWED"},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            rec := send(h, tt.method, tt.path, "", "")

            if rec.Code != tt.wantStatus {
                t.Fatalf("status = %d, want %d", rec.Code, tt.wantStatus)
            }
            if ct := rec.Header().Get("Content-Type"); ct != "application/json" {
                t.Fatalf("Content-Type = %q, want application/json", ct)
            }
            var body errorBody
            if err := json.NewDecoder(rec.Body).Decode(&body); err != nil {
                t.Fatalf("decode error body: %v", err)
            }
            if body.Error.Code != tt.wantCode {
                t.Fatalf("code = %q, want %q", body.Error.Code, tt.wantCode)
            }
        })
    }
}

What Is Still Wrong

Problem Where it is fixed
Error responses carry no request ID, so a client cannot quote it to support Chapter 8
Errors are built in two styles: handlers that write them and helpers that return them Chapter 8
Handlers still log with log.Printf instead of structured, request-aware logging Chapter 29
Anyone can call any endpoint Chapter 9
Logs are written synchronously to standard output with no sampling or limits Chapters 29 and 40

Engineering Lens

What problem did we solve? We gave every request an identity, a log line, and a guarantee that a panic becomes a well-formed error response, all without touching a single handler.

What complexity did we introduce? A layer of indirection that makes execution harder to trace by reading code, a request context that carries hidden values, and an ordering rule that is easy to get wrong silently.

What failure modes appeared? Panics that escape logging, wrapped writers that hide capabilities, client-controlled data flowing into logs, and path values lost by bypassing the mux.

What would break at 10× scale? Log volume. One line per request is cheap at a hundred requests per second and expensive at ten thousand, where sampling, levels, and log shipping become real costs.

When should we not use middleware? For behavior that applies to one endpoint, or that needs to know what the handler decided. Middleware is for concerns that are independent of what any particular endpoint does.

Exercises

  1. Re-add the /boom route and compare its behavior with and without recoverer in the chain. What does the client see in each case, and what appears in the log?
  2. Change the chain order to recoverer, requestID, requestLogger and run TestPanicIsRecoveredAndLogged. Explain in your own words why the final assertion fails.
  3. Write a middleware that sets X-Content-Type-Options: nosniff on every response. Where in the chain should it go, and does the position matter?
  4. Send a request with a 65-character X-Request-ID. Then craft one containing a space or a newline escape. What does the server do, and why is it unwise to trust the value?
  5. Remove the Unwrap method from responseRecorder. Write a handler that calls http.NewResponseController(w).Flush() and observe the difference.
